# Select the maintained engine on Waystone

The host manager can select the explicit `llama` CLI through the existing `chandra-waystone-worker.service` SSH lease and Windows Job. The node remains named `waystone`, with the usual forwarded worker and selected router URLs. This is an installation capability; its source tests establish no new numerical, Windows lifecycle, routed throughput or deployment acceptance. The current candidate's evidence and limitations remain in [the engine trial](sycl-engine-trial.md) and [adapter guide](../runtime/llama/README.md).

Supply the remote configuration path, its exact SHA-256, and a private local copy of those same bytes. The manager authenticates the local copy and derives execution/admission capacity from its integer `parallel_requests` field (1, 2 or 4). The unchanged Windows CLI authenticates the same SHA-256 and validates the entire remote configuration before creating a listener. A different remote profile cannot silently become the installed profile. The local copy is installation input only; subsequent service starts use the saved remote path/hash. Keep private configurations, lease tokens and installation backups outside public Git.

For C4, use the qualified configuration with `parallel_requests=4`. The manager sets worker `--queue-limit 3`, which admits four total jobs, and router Waystone `capacity=4`, `queue_limit=0`, `auto_queue_limit=0`, which admits those same four. It always passes normal `--idle-seconds 300`; it does not use the finite qualification wrapper. Existing NorthStone settings, router deadlines and scheduling cost remain intact. The old Waystone scheduling cost is preserved as an uncalibrated estimate for this new engine; explicit Waystone selection does not depend on it. An existing LAN binding must be supplied again with `--lan-address`, using the prior installation receipt. A fresh installation uses historical router defaults for the other node.

Provision a separate remote source directory containing the reviewed `chandra_service`, `runtime/llama`, `runtime/sycl` and required `runtime/native` modules, with the qualified Python dependencies. The existing historical `scripts/waystone/deploy_source.py` copies only the older XPU package and is insufficient for this route. A retained qualification package's `source` directory can be reused directly when its source identities and interpreter match the qualified candidate; invoke the production module from that directory rather than its finite wrapper. Keeping the historical remote checkout intact makes rollback independent of source replacement.

Before replacement, save both exact installed unit files, all three private `.local` files (`router.json`, `channel.json`, `installation.json`), their modes, checksums and current enabled/active states in a fresh private backup directory. Keep that backup through operational acceptance. The installation command verifies owned units, stops the old lease before replacement, and restores prior files and service states if its synchronous transaction fails. A successful systemd start does not prove that the remote service authenticated or became healthy, so the external backup is also necessary after a successful transaction.

Run from the Linux checkout after reserving the Windows GPU and checking the current processes. The variables below name the authenticated local copy, reviewed remote source/interpreter/config, existing SSH alias and retained LAN address; `LLAMA_CONFIG_SHA256` must identify the exact configuration bytes rather than a model or recipe hash.

```bash
.venv/bin/python scripts/host/manage.py install --worker-backend llama --ssh-host "$SSH_ALIAS" --remote-root "$WINDOWS_LLAMA_SOURCE" --remote-python "$WINDOWS_LLAMA_PYTHON" --llama-config "$WINDOWS_LLAMA_CONFIG" --llama-config-sha256 "$LLAMA_CONFIG_SHA256" --llama-config-copy "$LOCAL_LLAMA_CONFIG" --lan-address "$EXISTING_LAN_ADDRESS"
.venv/bin/python scripts/host/manage.py status
curl --fail --max-time 10 http://127.0.0.1:18001/health
curl --fail --max-time 10 http://127.0.0.1:8002/backends/waystone/v1/models
```

Retain cold health showing the authenticated profile's capacity and no loaded engine, then perform finite direct and selected-router requests with original pixels, full context/output allowance and no automatic retries. Confirm four overlapping requests and bounded fifth-request refusal, complete response content and usage, normal idle unload without health polling renewing the timer, and actual owned process retirement after service stop before accepting deployment. Use `http://127.0.0.1:8002/backends/waystone/v1` with model `chandra` for a stock CLI compatibility check. Its application retry setting is `MAX_VLLM_RETRIES=0`; the stock OpenAI SDK may still retry transport errors, so failure/no-replay qualification uses the existing direct HTTP harness instead. Broader dense-page content failures remain recorded independently of endpoint acceptance.

For rollback, first verify the saved checksums and that the current units still match their installation receipt, then stop both task-owned services and confirm the current Windows lease and owned model tree have retired. Restore the five saved files byte-for-byte with their original modes, run `systemctl --user daemon-reload`, restore each saved enabled state, and start only the units that were active at the backup boundary. Confirm the historical forwarded health is cold and the selected model route remains available. Do not reconstruct rollback with a historical `install` command: that route uses default router policy and can lose the retained NorthStone queue settings. The AMD gateway is independent of this transaction and retains its root-owned state.

The offline host checks exercise route authentication, deriving 1/2/4 admission from exact bytes, mixed-input refusal before installation, remote hash refusal before listening, preservation of the other node's router policy, normal idle arguments, and transaction failure restoring prior bytes/modes/states. Run the existing `tests/host/test_manage.py` together with `tests/llama/test_llama_launcher.py` after literal source review; all service, SSH and inference actions in these checks are fakes.
