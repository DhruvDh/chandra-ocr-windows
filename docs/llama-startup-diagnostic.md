This opt-in keeps the latest observed startup stage, native PID when actually returned by launch, startup-only native excerpts and retirement context on private local Windows disk. `manage.py install --worker-backend llama --llama-startup-diagnostic` passes the same explicit service flag. The service derives the fixed file from the authenticated configuration's parent; no arbitrary diagnostic filename, environment override or API route is added. Before listening, opt-in exclusively creates `llama-startup.private.json`; an old snapshot, reparse parent or fixed `.tmp` stops this new service before model creation. The Windows directory must already have the root-verified project-private owner/DACL; Python's mode 0600 alone does not create a private Windows ACL. On Linux the file is created mode 0600. No native text goes to a shared/public logger.

The file is ASCII JSON at most 128 KiB, plus one fixed at-most-128-KiB atomic temporary file. Each change flushes/fsyncs the temporary bytes and atomically replaces the snapshot. No timestamps in filenames, history directory, background writer, periodic observer or unlimited file accumulation is added. Normal service termination leaves the last completed snapshot; a kill during replacement may leave the preceding valid snapshot and a partial fixed temp. This is process-exit persistence, not a guarantee against disk, power, filesystem or machine failure. Root must preserve both files after an interrupted write. The latest engine generation within the same service replaces its predecessor; collect a failure before allowing another startup. Existing service restart policy is unchanged: a new outer process refuses the existing snapshot rather than overwriting it or starting another model.

Stages mark entry into input holding, full input authentication, second admission, native launch, returned native process and engine readiness. A null PID means no PID was observed; it does not assert global absence or rule out a partially created native child. A known partial-launch PID is retained through cleanup for that generation; original launch/closure evidence and subsequent retry-cleanup outcomes remain separate. Output uses the existing 64-KiB RAM tails, retaining at most 8,192 complete-line characters per stream in the file; clipped first and incomplete last lines are omitted, JSON control characters are escaped, and the actual internal API key and alias are redacted. No argv, environment, raw exception text, requests, images or responses are serialized. Native model paths may remain in startup output: keep this file private. After authenticated models/full-slot readiness and before ready is published or any native inference POST, native excerpts freeze. Later retirement updates only allowlisted state: stop/closed flags, observed exit code/PID, handle/active-process closure and held-file release. `closed` is only the worker's existing affirmative closure result, never inferred from a timeout or outer cgroup exit.

A required evidence write failure during startup fails that startup. Before launch it prevents a native child; after launch it requests owned stop and keeps draining/retiring the same child through the original ownership path. Retirement's own evidence-write failures log only a fixed safe message and do not replace the original exception or prevent cleanup. A stale snapshot does not prove the failed later write or remote closure; inspect its timestamp, stage and retirement fields together with the actual service/transport result. File I/O adds opt-in diagnostic overhead; it supplies neither a new timer nor stronger Windows API deadlines.
