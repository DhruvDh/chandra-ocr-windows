# Model-free final-page probe (native-0 failed-control follow-up)

The native-0 first-page control returned the expected IDs 2539 and 795 but failed the stronger control: after prefill and after one decode, tied-head shard 0's final row 26213 had a checksum mismatch and its SRV-copied bytes differed from the authenticated source in exactly 64 contiguous packed words (768 through 831, shard bytes 134213632 through 134213887, the start of the final half-filled 4 KiB page of a 134215680-byte buffer). The retained GPU words are 31 pairs of 0x24000006/0x00000008 and one 0x145a080f/0x00000000 pair at words 800/801, and the two GPU copies are byte-identical. This is a copied-byte difference on the common SRV path; it does not prove physical VRAM corruption, allocation overlap, driver cause or when the difference originated, and the cause remains unknown.

`ChandraNative/runtime/final_page_probe.h` (portable core and host-boundary contracts) and `final_page_probe.cpp` (Windows host) implement an inactive-by-default probe. Without `--execute` it returns the plan through `run()` with no host call: no Job screen, adapter enumeration, Device, listener or model. With `--execute --pci P --luid L --output O (--shader-root S | --direct-only) [--source-row source-row26213.bf16]` it first admits every file from memory, then requires an externally owned kill-on-close Job with a process memory limit of at most 1 GiB, selects the adapter through the strict `chandra::selectAdapter` with no fallback, and probes two contrasts in sequence with only one large buffer live: the original shape (requested ByteWidth 134215680) and a padded allocation (requested ByteWidth 134217728). Both use production buffer flags and a raw SRV with exactly 33553920 words, so the logical shape and SRV visibility are unchanged; the allocation padding is filled with a sentinel and recorded separately as a non-gating direct-copy observation. Input words are deterministic finite BF16 pairs from splitmix64; the admitted row 26213 source bytes are spliced at the final row only when supplied.

The repaired implementation was produced as local Claude task14; its original authoring report used the label Source12. This is separate from the HTTP task12. Independent source review accepted the repair against the rejected probe11 host (manifest 1cac423c22fa0d8bbf97901bdea23966c1939c2e95bd84416b5a1217b1022c64):

- Constant upload. The constant buffer keeps ByteWidth 256. Every upload is a zero-initialised 256-byte `Constants` object whose first eight words are the shaders' `cbuffer Params` ABI, and the host checks `GetDesc().ByteWidth == sizeof(object) == 256` before `UpdateSubresource`. The source11 shape (a 32-byte `params[8]` read as 256 bytes) is refused by that check, and the test runner's negative control shows that the old call shape overreads under AddressSanitizer.
- File admission. Source row and shaders are each read once through one handle into a buffer of pinned size plus one sentinel byte, so a large file is never loaded. Short, extra-byte, missing and unreadable (for example, directory) inputs are rejected explicitly, and the SHA-256 must match the pinned identity: source row 5120 bytes e696b6bda9b22dba3ad2a49132d6353302f5b20ad2627909ae5474586a46c07f; `runtime/weight_row_checksum.hlsl` 949 bytes ea462a1a71008cb56e86ce54f77fc7903ffa5a2e422ae722dfc1752a182e0c74; `runtime/weight_row_words.hlsl` 683 bytes 71fcda89e31d3c7a423bcb9ae73a9dc97cc89bd5463244dd9c965b5bbcd1fa97. Admission runs before the Job screen, adapter or Device and before the 128 MiB fill.
- Shader compile. The host calls `D3DCompile` on the admitted in-memory bytes with a null include handler, so the file is not reopened. A textual screen also refuses any `#include`, and compiled bytecode is capped at 16384 bytes.
- Bounds. Each SRV and UAV word count is checked against the buffer ByteWidth. Every `CopySubresourceRegion` box is checked against the queried source and destination ByteWidths, including alignment and 32-bit range.
- Timing. Each operation starts before its first `UpdateSubresource`, `Dispatch` or `CopySubresourceRegion` and ends after the completed event drain and Map copy-out. Dispatch/readback, direct-copy and churn operations are limited to 250 ms, and the upload and release operations to 2000 ms. The large COM objects leave scope before the labelled release operation starts; its 2000 ms entry covers ClearState and the event drain, and does not bound those preceding COM Release calls. An operation that is still pending at its limit, and a success that arrives after its limit, are both rejected. The run declares 32 operations (24 with `--direct-only`) with successful-operation sums of 15000 ms and 13000 ms respectively. Its 120000 ms cooperative host deadline covers adapter, Device, compiler, CPU fill and hash work, but starts after file admission and ends before JSON serialization and COM teardown. It cannot preempt a blocked driver call. Root must supply an independent finite wall timer covering the whole launched process and own its kill-on-close Job.
- Accounting. `requested_gpu_payload` sums the ByteWidths that can be live together (large 134217728, scratch 1048576, output 5120, staging 8192, constants 256). It does not measure driver or physical allocation. The `host_payload_bound` field is a forecast for input, admitted files, capped bytecode, readbacks, comparisons and report storage. Its 8x JSON DOM allowance is an assumption; the 1 MiB serialized cap is checked after serialization and before writing. Independent review found GCC vector capacity above one comparison object's formula, while the combined live comparison allowance still covered the two observed objects. Neither formula is a portable allocator proof. Process, compiler, runtime and driver allocation remain unmeasured and require the external Job limit.
- Direct copy independence. `--direct-only` admits and compiles no shader and creates no constant buffer. Each phase gates on the direct `CopySubresourceRegion` read, and churn copies the final row into scratch by the same API. Raw SRV and scratch UAV objects are still created but unused by this mode. Both modes share the Device, upload, driver and staging/Map path; sequential original/padded observations do not establish physical storage or exclude allocator-history effects.

Before and after a bounded churn (eight allocate-1-MiB, final-row-copy, release iterations, one scratch live at a time), each contrast compares the observations against the CPU bytes: an independent CopySubresourceRegion of the final row (5120 bytes, plus 2048 padding bytes for the padded contrast, at most 8 KiB of staging), the unchanged `weight_row_checksum.hlsl` screen over rows 26212 and 26213 (one group), and the unchanged `weight_row_words.hlsl` SRV copy of row 26213 (five groups). The host deliberately does not use the production Device class. The output records Job limits, adapter identity, UMD version, shader source and bytecode hashes, input hashes, requested buffer widths, readback hashes, per-operation timings and exact differing shard byte offsets. A passing synthetic probe cannot clear the trained failure, and no result claims physical storage or a cause.

CPU tests: `sh ChandraNative/runtime/final_page_probe_test.sh [source-row26213.bf16]` (GCC or Clang through `CXX`, ASan/UBSan). They exercise portable contracts, the fake constant-buffer upload, file admission against temporary files, `run()` with a counting fake host, and `timedOperation` with a fake clock and delayed fake calls. They do not execute D3D11. Independent source review reproduced the old constant-upload overread and accepted the repair for strict Windows build. Build25 then passed MSVC `/W4 /WX /fp:strict`, both FXC `cs_5_0` builds and inactive plans for both modes with no Device creation. The standalone probe is intentionally outside `build.cmd`; root owns each explicit build and hardware admission.

The first hardware attempt did not produce a usable measurement: its ownership lease ended early with EOF, leaving no synthetic result, process completion receipt or Job accounting receipt. A later Toolhelp snapshot found no remaining named probe and only its read-only helper among Python processes; that snapshot cannot replace the missing accounting or establish physical VRAM reclamation. A normal CPU-only ownership canary subsequently passed, while a controlled 1.25-second acknowledgement delay reproduced the client's one-second timeout and remote EOF retirement. This exposes a control-path weakness without assigning the cause of the original attempt. The ownership repair must pass finished review and CPU canaries before another finite model-free attempt. No successful probe result, trained numerical acceptance, OCR, endpoint or throughput improvement is claimed.
