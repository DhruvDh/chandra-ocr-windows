# Raise Intel’s sustained OCR throughput

Measure the largest sustainable number of correctly completed pages per second on Waystone’s Intel GPU, then change inference to raise that ceiling. Client requests in flight, queued pages and active GPU rows are separate quantities. More waiting work helps only while it keeps the inference engine supplied. AMD throughput tuning has stopped; load balancing can follow once individual node capacity is understood. The [work record](work-record.md) and [evidence index](../benchmarks/evidence/hillclimb-2026-10-04.json) state current outcomes and observation cutoffs.

The current target is native C++/HLSL DirectCompute/D3D11. The C1/C2 actor observations below are retained XPU history. Native trained correctness and endpoint acceptance remain open; there is no qualified native concurrency plateau or throughput gain yet. Apply this measurement method to the qualified native worker when it becomes available.

## Run the workload OCRd actually supplies

The recorded Zotero CLI pages use 1,624×2,100 pixels and 3,617 prompt tokens. The retained XPU page1 fixtures use 1,632×2,112 pixels and 3,959 tokens; those are separate inputs. Do not shorten output, resize pages or change precision to manufacture a gain. A separately identified precision candidate requires its own numerical and complete OCR qualification.

The inspected OCRd revision `2b9e892c53c0205d5476656ea6a514810c9da1c2` defaults to 15 document workers (`ZOTERO_OCRD_MAX_CONCURRENCY`) and one page per CLI batch (`OCR_BATCH_SIZE`). Each worker launches a Chandra CLI with up to `min(batch_size, 64)` request threads. Aggregate demand can therefore approach `document_workers × min(batch_size, 64)` pages, subject to available documents and admission. Keep both settings explicit; increasing both multiplies demand. Test the direct node endpoint before adding routing.

The current native source executes serial B1 with one active and one waiting request. Client concurrency can supply waiting work but creates neither a multi-row model invocation nor shared projection-weight reuse. The historical XPU worker executed one complete generation at a time; its isolated FFN experiment instead used at most two active rows with independent caches and static pairs, without refill within a pair. Its C1/C2/C4 harness admitted one, two or four requests; C4 supplied two queued requests while the same two-row actor ran. A native sweep must independently record active rows, queued requests and actual GPU invocation shapes. Any future true native batching requires memory forecasts, numerical comparison, per-page isolation and cancellation qualification.

## Accept useful throughput

The retained XPU diagnostic used two prime pages, two excluded warmup pages and sixteen measured pages in one once-loaded worker, alternating native and scanned page1. Independent closed C1 review verified sixteen complete, correct measured pages with genuine EOS in 2,451.5 seconds, followed by clean five-minute idle retirement, zero Torch allocations and owned process closure. Final root event counters were unavailable after cgroup removal. No ceiling or comparative improvement follows from that single observation. Its source audit found fresh image decoding, vision processing and text prefill on each request, without image-feature or prompt-embedding reuse. Repeated pixels remain an explicit corpus limitation even when those features are recomputed.

Keep a rolling window supplied: replace each completed page while work remains, without a client barrier after every pair. Preserve raw responses, unique request/worker identities, timestamps, finish reasons, usage, complete content/layout verdicts and producer EOS receipts. The primary finite rate is correct pages divided by the interval from first measured dispatch through the final complete validated response. Report setup/drain-inclusive rates separately. Rejection, timeout, truncation, replay, missing output or failed quality invalidates performance acceptance. Client completion alone does not prove backend drain.

Use initial points to select a fixed workload and bounded duration, then repeat near the apparent plateau in counterbalanced order. Predeclare the useful-gain threshold and uncertainty rule; five paired observations and a 5% threshold are starting choices, not completed validation. Call a plateau only when uncertainty excludes a useful improvement at tested higher concurrency. A resource-limited sweep establishes the best measured point and its unresolved bound. Before deployment, expand beyond the repeated page1 diagnostic to distinct prose, columns, equations, tables and unequal prompt/output lengths; qualify the exact isolated Chandra CLI outputs and metadata as well as endpoint responses.

## Use a roofline to choose inference changes

For arithmetic work `F` and memory traffic `Q`, intensity is `F/Q` and an isolated phase requires at least `max(F/P, Q/B)` seconds, using compatible arithmetic throughput `P` and bandwidth `B`. Model preprocessing, vision, text prefill and cached decoding separately. Match arithmetic roofs to actual shader precision, instructions and shapes; BF16 weight storage alone establishes no BF16 matrix or XMX compute ceiling. Allocation size is not memory traffic, and overlapping trace durations cannot be added into wall time. [Intel’s GPU optimization guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-0/optimize-memory-bound-applications-with-gpu.html) describes memory-hierarchy limits; [Time-Based Roofline](https://arxiv.org/abs/2009.04598) extends the model to dispatch and synchronization.

The [offline model](../benchmarks/roofline.md) derives 8,409,579,520 projection FLOPs per active decode row and 8,409,579,520 bytes of BF16 projection weights. Ideal sharing with `--batch` describes hypothetical true batching; `--queue-concurrency` leaves current serial B1 estimates unchanged. `capacity_terms.native_request_resident_cache.bytes_per_request.total` is 1,127,219,200 bytes, including four-byte KV storage for all 16,384 positions, recurrence and convolution history. The separate occupied-state fields cannot stand in for this fixed allocation or a total process-memory forecast.

For the original 3,617-token native0 prefix, `phases.text_prefill.native_chunked_prefill_per_request` reports 57 successive chunks with a final 33-token tail. Conditional one-sweep-per-chunk projection operands total 408,147,722,240 bytes, while the ideal whole-prefix single sweep is 8,409,579,520 bytes. Cache reuse and repeated shader operand requests prevent equating either term to measured off-chip traffic. The [conditional scenarios](roofline-scenarios.md) retain the explicit assumptions and omitted traffic; neither the fixed cache nor these sweep counts establishes observed fit, timing or sustained PPS.

Retained profiles identify many small decode launches and substantial skinny-matrix work, but profiling overhead prevents treating their uncovered spans as ordinary GPU idle. Measure unprofiled sustained rates first. Then test whether the traffic/launch model predicts an adjacent configuration; update it with actual compatible counters or bounded timelines where available. No empirical bandwidth roof or saturated hardware-wide pages-per-second ceiling is established yet. A larger batch, fewer dispatches or a compact kernel is useful only if it increases complete, correct throughput.
