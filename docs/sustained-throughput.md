# Raise each node's sustained OCR throughput

The target is the largest sustainable number of correctly completed pages per second on each node. Increase pages in flight until throughput stops improving, identify the limiting resource, and change the implementation or batching to raise that ceiling. Optimize NorthStone and Waystone separately. Load balancing can follow once their individual capacity curves are understood. The accepted three-request routing improvement measures burst completion time; it does not establish either node's throughput ceiling.

## Measure the serving system that OCRd uses

Keep client pages in flight, server queue occupancy, and active model sequences as separate quantities. NorthStone currently launches vLLM with `--max-num-seqs 2`, a 70% GPU-memory budget and prefix caching disabled. Its gateway admits up to eight pending or active requests. Waystone's worker holds an asynchronous lock around each complete `generate` call: it executes one page at a time, with two waiting slots by default. Increasing that queue cannot create a GPU batch. These are source-established configuration limits, not measurements of hardware saturation.

Use a direct single-node endpoint, bypassing automatic routing. First measure each installed configuration. Then test separately identified changes to actual engine capacity or batching; report the client-concurrency curve for each configuration. A plateau with two scheduled sequences is the ceiling of that configuration and workload, not an unrestricted maximum for the GPU. Never remove Waystone's lock and call simultaneous independent generations a validated batching implementation: model state, cancellation, stream ownership, peak memory and numerical behavior require a deliberate batch design.

The owner recalls a safe sweet spot of roughly 15 concurrent pages on the 7900 XTX in spring 2026. Treat that as a useful search region, not fresh validation of this runtime. The prospective NorthStone search should reach the neighborhood of 8, 12 and 16 active sequences when measured memory capacity and shared-machine availability permit; the installed two-sequence limit and eight-request gateway limit must not become artificial endpoints of the investigation. Engine capacity and gateway admission must be changed together in an isolated, identified configuration. Stock configuration changes can also alter compilation requirements, which belong in the resource plan. Waystone needs its own search after real batching is qualified. Choose the lowest concurrency near the best safe throughput plateau; additional waiting requests are useful only if they keep the engine supplied.

The inspected OCRd revision `2b9e892c53c0205d5476656ea6a514810c9da1c2` defaults to 15 document workers (`ZOTERO_OCRD_MAX_CONCURRENCY`) and one page per CLI batch (`OCR_BATCH_SIZE`). Each document worker launches an independent Chandra CLI; the installed CLI uses up to `min(batch_size, 64)` request threads and waits for the whole batch before proceeding. A normal daemon can therefore submit up to `document_workers × min(batch_size, 64)` page requests, subject to available documents and endpoint admission. This explains how the default configuration can supply approximately 15 pages in flight, but does not establish 15 active GPU sequences. Keep aggregate page concurrency explicit when tuning OCRd; changing both knobs can multiply the load. Other clients and one-off jobs fall outside that daemon bound.

The benchmark supplies a rolling window of requests, immediately replacing each completed page while work remains. There is no barrier after every small group of pages. Keep a fixed, balanced sequence of distinct synthetic pages and the same work count at every compared concurrency. Preserve page pixels, processor settings, prompt, BF16 precision, model revision and the normal 12,384-token output allowance. Include different image and output lengths, columns, equations and numerical tables; report results by page class as well as for the fixed mixture. A small-page-only run is a development result and cannot qualify the full workload.

Separate cold startup and warmup from measurement. Record compilation, prefix, image-processor and vision-embedding cache behavior independently; disabling text prefix caching alone does not establish a cache-cold image workload. The primary capacity measurement should represent first-seen document pages, with sufficient distinct inputs or a separately qualified cache policy. Repeated-page/cache-hot capacity is a separately labeled diagnostic. Do not flush caches opportunistically between favorable runs or use repeated identical pages as the main corpus.

Measure useful pages per second as the number of complete, correct pages divided by elapsed time from first submission through the final response. Preserve every request's raw response, identity, timestamps, finish reason, token usage and quality verdict. Include the initial window fill and final-drain costs in that finite-work rate and report a separately defined interior steady-state rate, occupancy and latency distribution. A rejection, timeout, truncated output, retry, missing page or quality failure invalidates the configuration's performance acceptance; it must not disappear from the denominator or inflate the score. Client completion is not proof that backend generation has drained after a timeout.

Use a short pilot only to choose a fixed work count and resource envelope before the comparison. Formal runs should contain several minutes of sustained work and many replacements per slot; a run dominated by its initial fill or final tail is insufficient. Sweep legal client concurrency upward, initially 1 and 2, then higher levels only within admission and memory limits. Repeat near the apparent plateau with the same work and counterbalanced order. Predeclare the minimum useful gain and uncertainty rule: a suggested starting point is five paired observations and a 5% improvement threshold. Failure to show a gain alone is not equivalence; call a plateau only when the uncertainty bounds exclude a useful improvement over the tested higher levels. If a resource or time limit prevents that check, report the best measured rate and the unresolved bound.

## A roofline model for the actual workload

For a phase with arithmetic work `F` FLOPs and device-memory traffic `Q` bytes, arithmetic intensity is `F / Q`. Its compute/bandwidth roof is `min(P, B × F / Q)`, using compatible arithmetic throughput `P` and bandwidth `B`. Equivalently, an isolated phase needs at least `max(F / P, Q / B)` seconds. Use the arithmetic actually executed: BF16 matrix operations, FP32 softmax and recurrent operations need appropriate roofs rather than a single marketing peak. Device allocation size is not memory traffic. These are standard roofline relationships; [Intel's GPU optimization guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-0/optimize-memory-bound-applications-with-gpu.html) also explains the importance of the memory hierarchy.

Model image processing, vision encoding, text prefill and cached decoding separately. Record shapes, true batch size, input tokens and generated tokens. Batching may amortize weight traffic across pages, but attention, recurrent state, padding and longer prefill increase other work and memory demand. Use source-derived operation/traffic estimates as estimates; replace them with measured evidence where supported. Fit phase observations at more than one concurrency and check the model's predictions against a held-out configuration before using it to justify an optimization.

The executable [offline model](../benchmarks/roofline.md) now derives partial phase costs from the pinned model's projection dimensions. Dense decoding projections require about 8.410 GFLOPs per active row; an ideal shared BF16 weight read is about 8.410 GB per batch step. True batching can therefore increase this component's arithmetic intensity approximately in proportion to batch size. Stored state adds about 50.3 MB per page plus 32 KiB per page token, before activations, workspaces and allocator overhead. These estimates explain why batching is worth investigating and why its memory cost must be measured. They do not provide a measured bandwidth ceiling or prove that a proposed batch fits.

The model also reports an additive [conditional cached-decode traffic scenario](roofline-scenarios.md), with batch-amortized weights, KV reads and writes, and FP32 recurrent matrix reads and writes. It counts `completion − 1` cached forwards because prefill produces the first completion token. The scenario document supplies precision-specific nominal vendor inputs and a batch-15 illustration; cache behavior, omitted traffic and unmeasured effective roofs prevent interpreting those ratios as sustained node ceilings.

| Limit | Evidence needed | What it would suggest |
| --- | --- | --- |
| Device bandwidth | Memory traffic and achieved bandwidth at a named memory level | Increase useful reuse, reduce traffic or improve access patterns |
| Arithmetic throughput | Executed operations, precision, matrix shapes and achieved rate | Improve batching or the compatible library/kernel path |
| Launch and synchronization | CPU submission timeline, device gaps and synchronization sites | Reduce dispatches or unnecessary synchronization |
| CPU pipeline | Render, encode, tokenize, upload and output-processing service time | Overlap or bound preprocessing without starving inference |
| Scheduling and memory capacity | Running/waiting sequences, cache/state footprint, VRAM and host RAM | Adjust engine capacity only where measured headroom permits |

For the fixed page mixture, aggregate per-page work gives an optimistic node bound such as `min(P / FLOPs_per_page, B / bytes_per_page)`. Mixed arithmetic and overlapping phases need separate resource demands; do not sum overlapping trace durations into wall time. Add serialized host/launch service limits when observed. A GPU can fall far below the arithmetic/bandwidth roof because it is waiting for dispatch or is constrained by sequence capacity. [Time-Based Roofline for Deep Learning Performance Analysis](https://arxiv.org/abs/2009.04598) provides a useful extension for those effects.

No empirical bandwidth roof, precision-specific compute roof or saturated pages-per-second ceiling has yet been established for this stack. Retained profiles identify candidates: Waystone has many small launches during decoding; NorthStone's earlier trace spends substantial kernel time in paged attention and skinny matrix operations. Those observations guide measurement but do not prove the bottleneck at saturation. Counter availability and profiler compatibility must be checked on the actual Radeon and Arc devices before claiming measured roofline efficiency.

## Qualification and shared-machine operation

Preserve the existing numerical gates and complete OCR checks for every new arithmetic, cache or batching path. Batched validation must additionally cover unequal prompt/output lengths, per-page state isolation, early EOS, cancellation, ordering and restoration. Memory reductions can enable useful batch sizes, but reclaimed allocator bytes alone are not a throughput improvement. Accept an optimization only after independent correctness, bounded resource behavior and repeated unprofiled sustained-throughput comparisons pass.

Another authorized task may stop NorthStone's sleeping OCR gateway to recover its retained host RAM for large benchmarks. This is a host-RAM reservation, not a reservation of both GPUs. Do not restart the local gateway against it. Waystone work remains independently eligible with a small, bounded NorthStone client and fresh checks of Waystone's resources. Recheck RAM, VRAM and process ownership before each admitted hardware phase; stop new admissions and drain owned work if limits are breached. Source analysis and small CPU tests can proceed without loading either model. Current priority work excludes driver changes, new custom kernels, stress tests and deliberate crashes.
