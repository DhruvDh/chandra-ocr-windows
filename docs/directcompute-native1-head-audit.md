# Native-1 failure: localization and the opt-in tied-head audit

This guide records what the closed native-1 failure packet establishes, what it cannot establish, and the bounded opt-in diagnostic intended to locate the first flagged stage of the tied-head path on Waystone. A completed native-0 two-prediction audit ran on the GPU and failed its stronger control; the closed evidence is retained below. No repair, root cause, trained numerical, OCR, endpoint or throughput qualification is claimed. No production default changed and the original ordinary-worker failure remains rejected and open.

## Original failure

The second original page, native-1 (input manifest SHA-256 `aab97d615f7e3181b9a3ef814f8784030f17fb186a31964df0a2a6063512e8d1`), ran as the first request of a fresh frozen Build20 resident worker with `gemv_b1_selection` `ordered`. All 1,952 generated IDs alternated 52427 and 0 from generated index 0 until root canceled the request at the finite deadline; it drained and retired at `text.layer.12`. Even indices chose 52427 with finite logits from 9.953037915854457e29 to 1.0101590720568703e31 while runner-ups stayed ordinary (23.25 at index 0, then 11.5625 to 14.375, the maximum at indices 1,946 and 1,948 of the generated-token journal, SHA-256 `58bb40af6cb00e27625827ae8127297da59ff43ca20c7024a7d87371d596f124`). Every odd index had all 248,320 logits exactly zero; `greedy()` refuses any nonfinite logit, so these were finite zeros, not NaN. No caller EOS appeared and none of the 18 content checks passed. The retained AMD response for the same pixels completed with 560 tokens.

The native-1 prompt IDs and derived positions are byte-identical to native-0's; only pixel values differ. Native-0 completed twice on the same Build20 tree, which includes the unqualified softmax barrier candidate `283d3356ea3c882517e96ddff26706bae21bfe3cd04a523fc065e9aa8183169e`, so that candidate is present in both the passing and the failing runs.

## What the packet establishes

Token 52427 is the final row of `embed_tokens` shard 1. The importer stores at most 128 MiB per shard; a 2,560-column BF16 row is 5,120 bytes, so each shard holds ⌊134,217,728 / 5,120⌋ = 26,214 rows (nine such shards plus 12,394 rows). Shard 1 covers rows 26,214–52,427 in 134,215,680 bytes, and row 52427 is its last 5,120 bytes. The tied head reads it in the ordered GEMV's last 614-output dispatch of shard 1 (group 76, owner 5), and the embedding lookup reads the same words through a different shader.

A single logit of 1e30 is impossible for authenticated weights unless the head reads different bytes, the head computes something other than the dot, or the final RMSNorm leaves its contract. The failed run recorded scalar summaries only: no final-norm row, full logit row or row bytes were retained. RMSNorm with gain 1+w gives ‖y‖₂ ≤ √N·max|1+w_d| for any finite input (finite overflow yields exact zeros; NaN is refused). Cauchy–Schwarz then bounds every correct head logit by ‖y‖₂‖W_r‖₂ plus the FP32/BF16 rounding term. Attention, the softmax barrier, recurrent state, vision and merge can only change y within that bound, and cannot raise one vocabulary column while leaving the runner-up ordinary. Native-0's final-norm rows have ‖y‖₂ between 106.6 and 162.7. If native-1's final norm had stayed at that scale and the head had computed a correct dot, the row the head read would need ‖W₅₂₄₂₇‖₂ ≳ 6.1e27 at index 0 and ≳ 6.2e28 later. That is a conditional bound on the bytes the head used, not an observation of the stored row.

One sufficient mechanism explains both halves of the alternation, and it remains a hypothesis. Suppose the embedding lookup and the head both read the same finite but enormous row 52427, large enough that each FP32 RMSNorm on the residual stream carrying it overflows Σx² to +inf. The scale is then exactly 0 and the output exact zeros, as in FP32 PyTorch RMSNorm. If later finite sublayers leave the residual that large, the final norm is zero, every logit is +0, and greedy picks ID 0 by its first-index tie rule. Token 0's ordinary embedding then restores ordinary logits except at column 52427. The CPU test demonstrates this conditional mechanism with a deliberately injected, aligned 2⁹⁰-scale row; it does not show that the real failure followed it. The scalar logs do not establish that the stored row itself became enormous rather than being misread, or that every element (or any particular element) exceeds √(FLT_MAX/2560) ≈ 3.65e17; a large L2 norm says nothing about how it is distributed. Finite sublayer additions can in principle cancel or lower a large residual, so the zero rows are not implied either. Nor does the signature show that a head-only or norm-only explanation needs a second, independent embedding fault: a common read path, shared device or process state, an arithmetic fault, or an observer effect could act on both reads. Read, arithmetic, observer and process explanations all remain open.

An all-zero final-norm row does not by itself establish that mechanism or any overflow. A zero pre-norm row has Σx² = 0 and also yields exact zeros, as do zero gains or other compute and read faults, so a zero observation is consistent with a huge row but is not a diagnosis of it. The audit reports such a row with its cause unknown and does not label it overflow.

In native-0's diagnostic process the same row was ordinary: logit 52427 was 0.80859375 at the last prefill (rank 35,623) and −2.30, −4.22, 1.66, −0.43 and −2.31 at decode steps 0–4. Every shard-first and shard-final row was ordinary too. Whatever produced the native-1 symptom did not appear in that process; whether the stored row, a read of it or something else changed is not known.

Root's later closed diagnostic06 observation ran native-1 itself in a fresh CLI process with a 14-token cap and selected-value observers. It reached the cap without reproducing the catastrophe. The six retained full-vocabulary rows begin with IDs 2539, 795, 1402, 361, 71 and 16, with ordinary logits (best 16.25–34.25, one maximum each), and logit 52427 between −4.16 and −1.41. The six retained final-norm rows have ‖y‖₂ from 102.1 to 162.1, and the 55 payloads hold no nonfinite value. Its process, observers and request shape differ from the failing ordinary worker, and those differences remain unassigned. This non-reproduction does not clear the ordinary-worker failure, assign a cause, or establish numerics, complete OCR, throughput or endpoint acceptance. Its tensors cannot stand in for the full logit rows the failed run never retained.

## What it cannot establish

Source review found no write, indexing, sharding, lifetime or readback route to that row. No production dispatch binds a weight shard as a UAV, and D3D11 discards raw UAV stores outside a view. The importer's offsets, word counts and uint32 byte ranges are exact. The GEMV and embedding indices stay inside shard 1, and `UpdateSubresource` copies a mapped view that is released only after a drain. The packet does not show whether the GPU-visible bytes were wrong after upload, changed later, or were misread by the projection. One notable host fact remains: after the 8.66 GB upload, sampled WDDM local usage was 37 MB; it rose to 9.17 GB during decode and fell to 58 MB after worker retirement. These process-level samples suggest residency changes during requests, but they do not show that any particular weight shard, including shard 1, migrated, or that residency affected the result.

## The opt-in audit

`chandra-inference.exe --head-row-audit` is accepted only with `--execute` and `--diagnostic-token-cap` 1 or 2, so it covers the last-prefill prediction and at most one cached decode prediction. The cap is also the number of predictions the audit must capture. Without the flag no new code runs, and the worker, defaults, selectors, allowance, context, precision, inputs and memory policy are unchanged. The code is [head_audit.h](../ChandraNative/runtime/head_audit.h), two integer-only shaders ([weight_row_checksum.hlsl](../ChandraNative/shaders/runtime/weight_row_checksum.hlsl), [weight_row_words.hlsl](../ChandraNative/shaders/runtime/weight_row_words.hlsl)) and the CLI glue in [inference.cpp](../ChandraNative/runtime/inference.cpp).

Before the importer runs, the CLI opens `model.safetensors` read-only without write sharing and holds it throughout, so the file bytes the importer hashes are the file bytes the audit reads. After import the audit streams all 248,320 authenticated head rows once in 4 MiB chunks, computing source-row checksums Σ(2i+1)·word (mod 2³²) and FP64 L2/L1 norms on the CPU. It also reads the final-norm gain to obtain max|1+w|. Every later authenticated row read is rechecked against its streamed checksum.

Three kinds of storage evidence differ, and reports keep them apart. Source-row checksums come from the authenticated file on the CPU. The GPU checksum screen recomputes them over every resident row at every checkpoint. A mismatch shows that the screen's read differs from the authenticated row; a match proves nothing, because multi-word changes can cancel in a 32-bit sum (a change confined to one word cannot). Exact comparison comes only from copied rows: at most 32 per checkpoint are copied raw by `weight_row_words.hlsl`, written as `head-row-audit/<checkpoint>.row<N>.gpu.bf16` with SHA-256, and compared word by word with the authenticated bytes. The import checkpoint copies checksum-mismatching rows. Each prediction copies the argmax, then the runner-up, then the checksum-mismatching rows, then rows whose logit violates its contract, in that order. Each copy records its reasons, `exact_match`, `differing_words`, the screen checksum, the copy's own checksum and the source checksum. `exact_comparison` lists identical rows, differing rows, differing rows whose checksum matched (`differing_rows_with_matching_checksum`), identical rows whose checksum mismatched, and mismatching rows left uncompared. Byte identity is claimed only for `rows_identical`, and only for what the copy dispatch read. Neither kind of GPU evidence establishes the actual GPU-visible bytes: both shaders read through the same SRV path the graph uses, so a common read-path fault would look like matching storage. No report claims full storage identity.

At each audited prediction the observer keeps the final-norm row of the same call, checked by tokens-before, generated-before and call length, and checks it against the RMSNorm contract. It records whether the row is all zero; the pre-norm row is not recorded (`pre_norm_row_recorded: false`). It checks every one of the 248,320 GPU logits against its Cauchy–Schwarz contract computed from authenticated row norms. It then runs the storage screen and copies, and recomputes the argmax and runner-up logits with the ordered GEMV's exact operation sequence and an a-priori error bound. Finally it runs the production `embedding()` operator for the argmax token and compares its bits with the authenticated row. The observer dispatches only on weight shards and new buffers, never on the observed value, and it drains through its own readbacks.

Bounds: checksum dispatches cover at most 1,024 rows of 1,280 packed words (K 2,560, within the K ≤ 9,216 and ≤1,024-output limits); there are 247 such dispatches per checkpoint (26 per full shard, 13 for the last). Readbacks are at most the 993,280-byte checksum vector, the 993,280-byte logits already read by greedy, ≤640 KiB of final-norm rows and ≤160 KiB of row copies per checkpoint. Host arrays total about 11 MB (four per-row vectors including the import screen, and one 4 MiB source chunk), and raw row files total at most 3×32×5,120 bytes. No whole-attention matrix, giant readback, weight copy or extra GPU weight allocation is made. The audit's own full-row reads may change WDDM residency, and both of its shaders read through the SRV path the graph uses. Neither the screen nor the copy separates VRAM contents from a page-level read fault.

`result.json` gains `head_row_audit`. `first_invalid_stage` is the earliest flagged stage, walking the import checkpoint and then each prediction's stages in the table's order, with every earlier audited stage showing nothing provably invalid. That is not proof that those stages are clean, and computation the audit does not sample (vision, merge, the text layers, attention and recurrent state) is not covered at all. `findings` lists every observed flagged stage, including those after an unobserved stage. Within a prediction the order is storage, final-norm contract, head, embedding and the all-zero row. The all-zero row is not provably invalid, so it is named only when its checkpoint is otherwise clean.

| `first_invalid_stage` | Observed evidence | Next step |
| --- | --- | --- |
| `tied_head_storage_differs_after_import` | A copied row differs from its authenticated bytes once import drained | Upload/initial residency or shared read path: test chunked or smaller uploads and a copy-engine readback |
| `tied_head_storage_changed_after_import@predictionN` | Import checksums matched; at the prediction a checksum mismatches and the copied row differs. The import checkpoint did not copy that row, so its earlier byte identity is unknown | Post-upload change, residency migration, unexpected writer or read fault; capture residency/ETW, inspect the raw dump |
| `tied_head_row_bytes_differ_with_matching_checksum@predictionN` | A copied row differs although its checksum matched here and at import | Collision or disagreeing reads; whether the difference existed at import is unknown because nothing was copied there |
| `checksum_screen_disagrees_with_exact_row_copy@after_import` or `@predictionN` | A checksum mismatched but the copy is identical to the authenticated bytes | Two GPU reads disagree (audit dispatch fault, transient read fault, bytes changing between reads); no storage difference established |
| `final_norm_hidden_outside_rmsnorm_contract@predictionN` | Nonfinite final-norm row or ‖y‖₂ above √N·max\|1+w\| | Norm or upstream fault; use `--diagnostic-dump` layer outputs |
| `head_projection_disagrees_with_authenticated_rows@predictionN` | A GPU logit is outside its bound from the authenticated row and no earlier audited stage is flagged. Only the rows actually listed in `rows_identical` had identical copied bytes; violating rows may remain uncopied under the 32-row limit | Investigate projection reads and arithmetic while retaining the uncopied-row and shared-SRV uncertainties; a different GEMV route is a separate diagnostic |
| `embedding_lookup_differs_from_authenticated_row@predictionN` | `embedding()` of the argmax differs; its copied row was identical | Embedding read path |
| `final_norm_hidden_all_zero_cause_unknown@predictionN` | Every final-norm value is exactly zero; nothing provably invalid in that checkpoint | Cause unknown: a zero pre-norm row is legitimate, FP32 Σx² overflow (for example from a finite huge stored row) also gives zeros; record layer 31's output with `--diagnostic-dump` |
| `audit_incomplete` | A requested checkpoint or stage was not audited before any finding | Not clean and not a non-reproduction; read `incomplete_reason`, `audit_errors` and `findings` |
| `no_invalid_value_in_audited_head_path` | Every requested checkpoint completed with nothing provably invalid | Not reproduced, not clean: identity holds only for what the copy dispatch read of the copied rows, unsampled stages are not covered, and the audit's reads may have changed residency and timing |

Completeness is the audit's own record, never inferred from how the run ended. `audit_complete` is true only when the import checkpoint and all `predictions_requested` predictions finished every stage without an audit error. The report also carries `predictions_started`, `predictions_audited`, `import_audited`, `audit_errors`, `incomplete_reason` and `run_end`. `run_end` is `completed` when `generate()` returned, `failed` with its error, or `unreported`. A run that stops early still leaves the audit incomplete. That includes a caller EOS before the cap, a cancellation, an exception in the graph or the audit, and a failure before the auditor exists, for which the CLI keeps a `head_row_audit` placeholder reading `audit_incomplete`. A failed prediction keeps a partial checkpoint (`complete: false`, `error`) holding only what was observed. A finding observed before the failure, with every earlier audited stage observed and unflagged within its limits, remains `first_invalid_stage`, and `audit_complete` stays false. The first completed or failed `finish` closes the audit; repeating it returns the same report, a conflicting run end is refused, and later observations are refused. Observations before a completed import, logits without their own call's final-norm row, and any observation after an audit failure are refused and recorded rather than silently skipped. Observations past the requested predictions are ignored without readback.

The raw dumps retain the bytes read by the copy shader for the selected rows. A structured pattern can suggest a discriminating test, but does not establish physical storage corruption, an earlier replacement, or its cause; the checksum, copy and graph share an SRV read path.

## Root-owned capture recipe

Build the reviewed checkout with the ordinary script, which also compiles every `shaders\runtime` file with strict FXC `cs_5_0`:

```bat
ChandraNative\runtime\build.cmd "%CHANDRA_FRESH_BUILD_DIR%"
```

Run the native-0 control first in a fresh process. Proceed to native-1 in a separate fresh process only after that control satisfies its stated gate. Use the frozen worker's GEMV route. Set `CHANDRA_PCI` and `CHANDRA_LUID` from a fresh adapter enumeration on the current boot, verified as the A770, immediately before the run. Never reuse a recorded LUID: LUIDs change across boots.

```bat
set CHANDRA_EXPERIMENTAL_GEMV_B1=ordered
chandra-inference.exe --execute --head-row-audit --diagnostic-token-cap 2 --model-dir "%CHANDRA_MODEL_DIR%" --shader-root "%CHANDRA_SHADER_ROOT%" --input-manifest "%CHANDRA_NATIVE0_MANIFEST%" --input-sha256 "%CHANDRA_NATIVE0_SHA256%" --output-dir "%CHANDRA_FRESH_AUDIT_NATIVE0_DIR%" --pci "%CHANDRA_PCI%" --luid "%CHANDRA_LUID%"
chandra-inference.exe --execute --head-row-audit --diagnostic-token-cap 2 --model-dir "%CHANDRA_MODEL_DIR%" --shader-root "%CHANDRA_SHADER_ROOT%" --input-manifest "%CHANDRA_NATIVE1_MANIFEST%" --input-sha256 aab97d615f7e3181b9a3ef814f8784030f17fb186a31964df0a2a6063512e8d1 --output-dir "%CHANDRA_FRESH_AUDIT_NATIVE1_DIR%" --pci "%CHANDRA_PCI%" --luid "%CHANDRA_LUID%"
```

Each run should take about the failed run's vision and prefill time (≈223 s and ≈168 s), plus import, one decode step and seconds of audit work. Keep the usual finite Job, commit limits and deadline. The native-0 control must report `audit_complete: true`, `predictions_audited: 2`, `no_invalid_value_in_audited_head_path`, zero checksum mismatches at every checkpoint, every copied row `exact_match`, bitwise-equal head recomputes, and IDs 2539 then 795 (logits 29.125 and 29.25). That checks the checksum shader across all 248,320 rows. The raw-copy shader is checked only on the explicitly selected rows; neither establishes uncopied-row identity or physical VRAM contents. Any `audit_incomplete` is neither clean nor a non-reproduction. If native-1 reports no invalid value, record it as non-reproduction, not acceptance, alongside diagnostic06; choose the next bounded experiment for a specific unresolved discriminator rather than repeating a whole-model capture without one. Either way the CLI process differs from the failing ordinary resident worker, so no audit outcome clears that failure. A diagnostic token cap makes neither run a page or throughput observation.

## CPU evidence and limits

Root's Build22 compiled source07, which independent review later rejected on three classifier defects. Claude Opus 5.5 implemented source08's repairs; independent review accepted its exact frozen code only for an externally guarded private two-prediction capture. Fresh Build23 authenticated that source, passed MSVC `/W4` and changed-CLI `/W4 /WX`, and compiled both unchanged audit shaders with strict FXC `cs_5_0` `/O3 /Gis`. The first real capture then failed its native-0 control despite returning the expected two token IDs: one copied row differed from the authenticated source at both predictions. The [closed control evidence](../benchmarks/evidence/directcompute-first-page-head-audit-failure-2026-10-06.json) records that result. Further whole-model progression is held; there is no clean-control, numerical, OCR, endpoint or throughput acceptance.

The following describes source08's CPU suite; independent review separately reproduced the classifier counterexamples and accepted their repairs for the limited private-capture scope. `sh ChandraNative/runtime/head_audit_test.sh` builds with GCC, `-Werror`, ASan and UBSan. It links the unchanged `operators.cpp` and `diagnostics.cpp` plus a test-only Device, and passes 526 checks. Using the real importer plan, it checks that 52427 is shard 1's final row and where the ordered GEMV covers it. It shows that a deliberately injected finite 2⁹⁰-scale stored row is sufficient to produce the alternating signature, and that a zero pre-norm row gives the same all-zero final norm without overflow. It covers the contracts' soundness and exhaustive single-word checksum sensitivity. It reproduces the reviewer's two-word collision on row 88 and covers three-word collisions before import, runner-up and contract-violating-row collisions, a collision at prediction 1, and an uncopied collision that stays outside the identity claim. It also covers a checksum read that disagrees with an identical copy, legitimate and overflow-produced zero rows, and a wrong logit outranking a zero row. Completeness cases cover zero, partial and complete cap1/cap2 runs, early stop, cancellation, and readback failures in the screen, the embedding and the final-norm read. They also cover import source and copy failures, repeated and conflicting finishes, the CLI placeholder, and observer ordering. The reviewer's closed counterexample harness, compiled against the repaired tree, now reports the collision, the zero row and the missing predictions as above, and its embedded suite passes. Thirteen mutation probes each restore one defective behavior, and every probe fails the suite. The test emulates shaders on the CPU. It does not prove FXC compilation, Intel execution, D3D11 residency behavior or the CLI's Windows glue, which remain root-owned.

Fresh trained-vector numerical qualification, whole-corpus acceptance, native HTTP acceptance and sustained throughput remain open, as does the native-1 failure itself.

## First hardware control: rejected

The original native-0 input retained its 1,624 × 2,100 image, 3,617 prompt tokens, 16,384-token context and normal 12,384-token output policy; the explicit diagnostic cap stopped this capture after two predictions. After import, all 248,320 row checksums matched, and no raw row was copied. At both predictions, checksum and raw-copy observations differed from source for row 26,213, shard 0's final row. Exactly 64 contiguous packed words, indices 768 through 831, differed; both retained GPU copies were byte-identical. The block starts at shard byte 134,213,632, exactly 128 MiB minus 4 KiB, while the shard ByteWidth is 134,215,680, 128 MiB minus 2 KiB. Its repeated structured words give a useful location and pattern for a model-free direct-copy versus SRV-read experiment, with a padded allocation as a separate contrast. They do not establish a driver fault, physical overwrite, allocation alias or when the difference began.

The selected argmax and runner-up row copies matched source, their ordered CPU head recomputes matched the observed logits bitwise, and final-norm rows were finite within the checked bound. IDs were 2539 and 795, but logits differed from the historical first-page run. These limited agreements do not override the mismatching row or qualify the complete page. The native process retired and drained, the external Job closed with zero owned processes, and the ordinary service was restored cold. The source-row extraction was a small CPU read whose bytes matched the auditor's authenticated source hash; it did not repeat the whole-model SHA-256.
