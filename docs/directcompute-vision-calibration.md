# DirectCompute vision attention dispatch calibration

[vision_dispatch_calibration.cpp](../ChandraNative/runtime/vision_dispatch_calibration.cpp) is a finite, model-free, opt-in native calibration of the four production vision attention shaders at the exact Zotero CLI workload shape. The recorded CLI request (decoded RGB 1,624 × 2,100, 3,617 prompt tokens) has grid `[1,126,96]`: 12,096 original patches in one frame, 3,024 merged rows, 378 query tiles of 32 rows and 95 key tiles of 128 keys (the last holds 64). The tiny request (grid `[1,32,26]`, 832 patches) has 26 query tiles and 7 key tiles, so it cannot validate the CLI shape. The calibration runs one production query tile per phase against complete K/V. It does not load a model, read weights or pixels, run the complete vision graph, or run all query tiles. The [closed October 6 record](../benchmarks/evidence/directcompute-vision-dispatch-2026-10-06.json) now qualifies Windows compilation, 14 inactive/refusal cases and all 16 model-free GPU dispatches on the A770. It establishes production-shape synthetic kernel checks and single-tile timing; trained activations, full-model fit, complete OCR and page throughput remain open.

## Source investigated

`VisionModel::attention` ([vision_model.cpp](../ChandraNative/runtime/vision_model.cpp)) runs, for each frame and each query tile at `first = 0, 32, …`, with `Q = min(32, L − first)` queries, `16Q` query heads and `T = ceil(L/128)` key tiles: allocate scores `[16Q·L]` and partials `[Q·1024·T]` as fresh R32 buffers; dispatch `runtime/vision_attention_scores.hlsl` (SRV q, k; UAV scores; groups `T × 16Q`), `runtime/vision_attention_softmax.hlsl` (UAV scores in place; groups `16Q`), `runtime/vision_attention_values.hlsl` (SRV scores, v; UAV partials; groups `T × 16Q`) and `runtime/vision_attention_reduce.hlsl` (SRV partials; UAV global result; groups `ceil(Q·1024/256)`); then drain once and release the tile scratch. The first and third use the 48-byte `AttentionParams {frame first, L, first, Q, 0, 0, 0, T, 1024, 16, 64, 0}`; softmax uses `{16Q, L, 0, 0}`; reduce uses `{Q·1024, frame first + first, T, 0}`. `VisionLimits` defaults are 32,768 patches per request and frame, row tile 512, query tile 32 and key tile 128 (enforced). Q and K come from `vision_rope.hlsl` after `vision_bf16` rounding and V is copied from the BF16-rounded QKV projection, so all three are BF16-representable values in R32 storage.

The scores shader stages one 64-float query vector in groupshared memory and sums 64 `precise` FP32 products per key, then multiplies by 0.125. Softmax runs 128 lanes per query-head row: a strided maximum, a seven-level max tree, `exp(score − max)` written in place with a lane-sequential `precise` sum, a seven-level sum tree and an in-place FP32 division. Values sums `probability × v` in ascending key order inside each 128-key tile from +0. Reduce sums the T tile partials in ascending order from +0 and applies `vision_bf16` (RNE, quieted NaN) at the SDPA output boundary. These five shader files are frozen by SHA-256 in the calibration source and in the plan:

## Phases

Phases run in increasing work order. Each grid passes the unchanged `VisionModel::forecast` admission, and each selected tile is one actual production tile for that grid.

| Phase | Grid(s) | Frame start, L | Query start, Q | Key tiles (last) | Fixture |
|---|---|---|---|---|---|
| `tail_two_frame_L200_q192_nonuniform` | `[1,4,6]`, `[1,10,20]` | 24, 200 | 192, 8 | 2 (72) | nonuniform |
| `tiny_L832_q416_nonuniform` | `[1,32,26]` | 0, 832 | 416, 32 | 7 (64) | nonuniform |
| `tiny_L832_q800_uniform` | `[1,32,26]` | 0, 832 | 800, 32 | 7 (64) | uniform |
| `cli_L12096_q12064_uniform` | `[1,126,96]` | 0, 12,096 | 12,064, 32 | 95 (64) | uniform |

The tail phase uses a second frame, so it covers a nonzero frame offset as well as query and key tails. The CLI phase uses the last query tile, which reaches the highest Q and result addresses. Every phase allocates Q, K, V and the result at the full `[patches, 1024]` production size. Scores and partials have the production tile sizes. Q rows outside the tile and K/V rows outside the frame hold a quiet-NaN poison, so any wrong row read propagates NaN. Scores, partials and the result start as the signalling-NaN sentinel `0x7fbadbad`, which these shaders cannot write for these inputs. Production buffers are uninitialized; initial data is a calibration-only creation argument and does not change any dispatch argument.

## Execution, gates and receipts

The executable is inactive without `--execute` and prints a CPU-only plan (`device_created: false`, 16 planned dispatches, footprints, frozen hashes, screens and per-block counts). Arguments are exactly `--execute`, `--shader-root`, `--pci`, `--luid` and `--output`, each at most once. Each option needs a following value that is present, nonempty and not option-shaped (no leading `-`, which no valid pin or absolute path has), so `--pci --execute` or `--pci --unknown` exits 1 instead of swallowing the flag as a value. Unknown, duplicate, valueless and stray arguments also exit 1. Pin syntax and absolute path syntax are checked with or without `--execute`, so the inactive plan is printed only for genuinely valid arguments; existence and freshness are execute-time checks. Execution requires an absolute shader root, lowercase PCI `bb:dd.f` and LUID `hhhhhhhh:llllllll` in the `adapter_identity.h` spellings, and an absolute, fresh (`CREATE_NEW`) receipt path whose parent exists. All of these are checked before any receipt or Device exists. The source then starts its 120-second deadline and hashes the five shader files under the shader root. If any byte differs from the frozen table, it refuses before creating the Device. A CRLF checkout would also be refused. The Device compiles the files at first dispatch, so root must keep the authenticated tree immutable during the run.

Each stage runs alone in its own profile window: `beginProfile` (which drains), the single production dispatch, then `finishProfile` (which drains and rejects a disjoint window). The window must contain exactly one dispatch with the expected shader and groups and a finite nonnegative duration. Otherwise admission fails, including a missing measurement or one for a different geometry. Receipt persistence and `beginProfile`, whose drain can wait for the Device timeout, can each block. So immediately before every submission the source rechecks its single absolute 120-second deadline twice: after the pre-dispatch receipt persistence and again after `beginProfile`. An expired deadline refuses that stage before its dispatch call. The refusal records `refused_before_dispatch` and `dispatch_call_started: false`, and nothing further is submitted; the entry's single bounded failure drain follows. Each Device allocation is also admitted against the deadline immediately before the call. The deadline is never reset or extended, and nothing is replayed. A call already blocked inside the unchanged Device, driver or compiler cannot be interrupted by the source and remains bounded only by the external Job. A completed duration at or above 100 ms stops before any further dispatch. The stage output is then read back and checked. A failed check also stops before the next dispatch. Before each phase after the first, every stage is extrapolated linearly in its work units (multiply-adds, exponentials or reduce additions) from the completed reference phase with the most units, times a declared margin of 2. If any prediction reaches 100 ms, the larger phase is refused before allocation. The margin is a refusal-only heuristic for the cache regime change: K and V grow from 3.4 MB each at L = 832 to 49.5 MB each at L = 12,096, and the score plane to 24.8 MB, all above the A770's 16 MB L2. It does not establish safety by itself. Buffers are released and the Device drained after every phase, and tracked bytes must return to zero. There is no warmup, retry, replay or fallback.

The receipt is rewritten and flushed before each dispatch and after each check. Each stage records whether its dispatch call started, whether it was submitted, whether it completed and was measured, the GPU profile, its duration, host submit-to-drained and readback times, and derived rates. If the calibration run throws after the Device exists, the inner handler first persists `FAIL_OR_INCOMPLETE` with the error and `retirement_required`. Next it makes one bounded `drain`, recording its outcome without resubmitting anything, persists again and exits 1 before the Device destructor can block. Other failures use the outer handler instead: Device construction, the initial identity and memory queries and their receipt write, and the final drain, tracked-byte check and memory query after a completed run. That handler persists the failing receipt only after the Device scope has unwound, so the destructor runs first, and then exits 1. Receipts are serialized through a counting sink that keeps at most 8 MiB and never builds a second unbounded copy. A report that would exceed the cap is replaced by a failing `RECEIPT_OVERSIZE` summary with `passed: false`, `retirement_required: true` and `detail_lost: true`, never by truncated JSON. The summary keeps only bounded fields: the full serialized size; the original state and error as UTF-8-safe, escape-aware excerpts of at most 4,096 serialized bytes, each with its full byte length and SHA-256; the dispatch counters; the failure-drain scalars; and the eight largest top-level fields with their sizes. The summary is itself checked against the cap, with a constant last-resort summary behind it. Exception text stored in a live report, and printed to stderr, is unchanged up to 64 KiB. Longer text is cut at a code point and gets an explicit `[ERROR TRUNCATED, detail lost: N bytes, sha256 …]` suffix. Every initial, progress and final receipt must be complete. A write that fits only the summary fails the run before any further dispatch, so an oversized final report cannot exit 0 or claim a pass. Receipts within the cap are byte-identical to the previous serialization. Memory fields report the Device's DXGI local budget and usage for this process on the pinned adapter, not global free VRAM. Accepted fields remain false for the full model, trained numerics, OCR, data-dependent speed, end-to-end performance and sustained throughput.

## Numerical checks

The public generator `public_lowbias32_bf16_dyadic_attention_v1` is a function of absolute row and column only. Nonuniform Q and K values are `i/4` with `i ∈ [−8, 8]`. Uniform Q repeats `g/4` (`g ∈ [−4, 5]`) across each column pair. Uniform K pairs are `(b + d)/4, (b − d)/4`, with `b` fixed per head and pair and `d` varying per key row. Every key therefore gets the same nonzero score `Σ g·2b/128`, which differs between rows and heads (range −130/128 to 118/128 in the CLI tile). V is `±m·2^−s` with `m ∈ 1…15` and `s ∈ 3…8`. All inputs are BF16-exact, as production RoPE/QKV outputs are BF16. V values and the uniform scores are guaranteed nonzero; the generator permits zero Q and K entries. Every score product is an integer over 16, and every partial sum stays below 4096/16. No score operation therefore rounds in any order, even if contracted, and ×0.125 is exact. Input buffers are committed by SHA-256 over their little-endian words.

| Stage | Rule | Kind |
|---|---|---|
| Scores, complete `16Q × L` plane | integer dot over 64 columns / 128 from the generator; uniform identity re-proved at every key | bit-exact, expected and observed SHA-256 retained |
| Probabilities, complete plane | binary64 softmax from the exact scores; derived screen below | screen; observed SHA-256 retained |
| Probabilities, uniform phases | every word identical across the complete plane | bit-exact |
| Value partials, complete `T × Q × 1024` | ascending FP32 `sum + p·v` from +0 per 128-key tile, D3D11 subnormal flush, from the observed probabilities | bit-exact, conditional on observed probabilities |
| Result, complete `[patches,1024]` | ascending FP32 tile sum from +0 then `vision_bf16` for tile rows; sentinel for every other row | bit-exact, conditional on observed partials |
| Selected output | binary64 attention `O = Σ p v` from the exact scores; derived screen below | independent screen |

The screens are derived a priori from the shader operation sequence and named per-operation assumptions, with no fitting to observations. Let u = 2^−24. The assumptions are these. First, FP32 add, subtract and multiply round to nearest even without contraction under `precise`; this is the D3D11 rule, consistent with the native bit-exact order-sensitive GEMV phase. Second, HLSL `exp` lowers to `2^(x·fl32(log2 e))`. Third, the `exp` (2^x) instruction's relative error is at most Z = 2^−21; this is my reading of the Direct3D 11 precision requirement and covers a 3-ULP bound, and review must confirm it against the D3D11.3 functional specification. Fourth, FP32 division is within 2.5 ULP (Φ = 2.5·2^−23 relative). The fixture verifies that `x_k = s_k − max` is exact. The rounded product with `fl32(log2 e)` shifts the exponent argument by at most `τ_k = |x_k|·log2 e·(2u + u²)`, so each computed exponential has relative error at most `D_k = 2^τ_k (1 + Z) − 1`. Each term passes through at most `n = ceil(L/128) − 1 + 7` sum roundings: a lane-sequential sum from +0 whose first add is exact, then seven tree levels. The sum error is therefore at most `γ_n = nu/(1 − nu)` relative. With `D = max D_k` over the row, a probability lies within `B_k = max((1+D_k)(1+Φ)/((1−D)(1−γ_n)) − 1, 1 − (1−D_k)(1−Φ)/((1+D)(1+γ_n)))` of the exact softmax. A device probability is accepted when `|p̂ − p| ≤ (B_k + 2^−36)·p`. The 2^−36 allowance covers the Neumaier-compensated binary64 oracle and is far below every screen.

For uniform rows B is 1.73e−6 (29u) at L = 200, 2.03e−6 (34u) at L = 832 and 7.27e−6 (122u) at L = 12,096. Dropping one key from the denominator shifts every probability by 8.3e−5 at L = 12,096, eleven times the screen, and dropping one lane of 128 shifts them about a thousand times the screen. Nonuniform screens reach 4.30e−6 (tail) and 5.20e−6 (tiny), dominated by the argument term at |x| near 10. In the CPU fake, an exp error of 2^−21 on even keys passes at 0.23 of the screen. An error of 2^−14 fails at the softmax stage, as does a lane dropped from the denominator.

For the output, each term has at most `128 + T` roundings: one product, up to 127 in-tile additions after the exact first, and up to `T − 1` tile additions. So `|Ô − Σ p̂ v| ≤ γ_{128+T} Σ |p̂ v|`, and `E = Σ B_k p_k |v_k| + γ_{128+T}(Σ p_k|v_k| + Σ B_k p_k|v_k|)` bounds `|Ô − O|`. BF16 RNE adds at most 2^−8|Ô|, so the stored value must satisfy `|b − O| ≤ 2^−8(|O| + E) + E + 2^−36 Σ p|v|`. BF16 rounding dominates this screen. A result near a BF16 rounding boundary reaches 0.76–0.98 of it in the CPU fake, which is expected of a rigorous bound and does not show fragility.

Exact rules hold only under the stated D3D11 arithmetic. The exact check of the values stage is conditional on the device's own probabilities, and the reduce check on its own partials. Each is end-to-end exact only together with the independent screens. The uniform fixture exercises actual memory and index geometry at the full 12,096-key shape: every K, V and score row is read, and the result rows outside the tile are compared. It cannot detect a K row error that preserves pair sums, and it does not test the max subtraction. The nonuniform tail and tiny phases cover those properties at smaller shapes. No fixture establishes equivalence with trained activations, trained-data softmax error, or data-dependent speed. Uniform scores make every exponent argument zero, so the full-shape timing may differ from timing on trained data.

Per-block multiply-adds and dispatch counts equal the unchanged `VisionModel::forecast` (299,649,466,368 and 1,512 for the CLI grid). The CLI block is about 211 times the tiny block. In the CLI dispatch-unique model, K and V are re-streamed by every one of the 378 query tiles, 37.5 GB per block. The materialized 24.8 MB score plane costs four plane transfers per tile (scores write, softmax read and write, values read), another 37.5 GB; partials add 9.4 GB. Softmax actually issues three reads and two writes of the plane. At the A770's nominal 560 GB/s ([roofline scenarios](roofline-scenarios.md)), 84.4 GB is about 151 ms per block, or 3.6 s for 24 blocks. The 599 GFLOP per block are scalar FP32 `precise` work, not XMX. The repository records no FP32 vector rate; the 34.4 TFLOP/s FP16 vector figure is only an upper bound and gives a floor of about 17 ms per block. Each receipt stage reports multiply-adds, issued and dispatch-unique bytes per measured millisecond, so root can place the measured tile on these axes.

The receipt's `cli_attention_projection` multiplies the measured CLI tile by 378 tiles and by 24 blocks. It is a labelled linear projection, not a measurement. It excludes per-tile scratch allocation, two WDDM budget queries, submission, the per-tile drain, inter-dispatch gaps and other vision operators. Those operators are patch embedding, QKV, projection, MLP and the merger. It also excludes text prefill and up to 12,384 decoded tokens, image preparation, transfers, queueing and concurrency. The production graph drains once per tile, 9,072 times per CLI image. The Device drain polls with 1 ms sleeps, so host drain latency is on the critical path; this calibration's host submit-to-drained times only sample it. Timings come from one isolated tile per shape with drains between stages, at whatever clocks and cache state the device has, and the first phase's host times include shader compilation. None of this is a sustained pages-per-second result. That still requires repeated, uninstrumented complete pages at safe concurrency.

## CPU checks

`ChandraNative/runtime/vision_dispatch_calibration_test.sh FRESH_DIRECTORY` needs only g++, clang++ and Python 3. It builds [vision_dispatch_calibration_test.cpp](../ChandraNative/runtime/vision_dispatch_calibration_test.cpp) with g++ and clang++ under `-Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion -Wshadow -Werror`, and again with clang++ ASan/UBSan. The unchanged `vision_model.cpp` and `operators.cpp` are compiled with `-Wall -Wextra -Werror`, plus `-Wno-dangling-reference` for a GCC false positive in `vision_model.cpp`. The [test-only fake Device](../ChandraNative/runtime/vision_dispatch_calibration_fake_device.h) has two modes. In record mode it traces dispatches; in execute mode it runs C++ transliterations of the four shaders under D3D11 binary32 rules (sign-preserving subnormal flush), bounds-checks every raw load and store, and fails on duplicate stores. The transliterations test the algorithm, addressing and host control flow, not fxc, the driver or the A770.

The suite covers the following:
- SHA-256 against FIPS vectors, and the frozen hashes against this checkout; a single changed byte and a missing include are refused.
- Phase geometry, and the unchanged production forecast against the recorded CLI forecast: 12,096 patches, 3,024 merged rows, 49,545,216-byte maximum buffer, 291,337,280-byte workspace, 1,512 dispatches and 299,649,466,368 multiply-adds.
- Generator ranges and BF16 exactness, and the uniform identity.
- The derived screen magnitudes and sensitivity.
- Strict argument and pin admission. This covers the review's `--pci --execute` and `--pci --unknown`; option tokens, empty and missing values in each value position; unknown, stray, `=`-form and duplicate arguments; pin and path syntax without `--execute`; and valid inactive and execute arguments in any order.
- The unchanged `VisionModel::firstBlock` on the record-only fake for each phase's grid. Each calibration tile's role-normalized transcript (shader, every cbuffer word, groups, SRV/UAV roles and buffer sizes) is byte-equal to the production tile, and production drains after every tile.
- Direct oracle-helper checks: single-bit flips are located, a write outside the tile is caught, and a probability moved by 0.5 and 2 times its own screen is admitted and refused respectively.
- Fourteen fault and gate cases that each stop at the expected dispatch.
- Deadline boundaries. The cases are both review counterexamples (expiry in the pre-dispatch receipt and after the completed scores check), real elapsed-time expiry inside `beginProfile` at profile windows 1, 3 and 6, and expiry after a completed phase. They stop after 0, 1, 0, 2, 5 and 4 dispatches respectively. In each, nothing reaches the Device after the expiry, no later stage or phase starts, the receipt records the refused stage, and one bounded failure drain releases every buffer.
- Receipt bounds. The review's exact receiptCap+1 error becomes a 6,719-byte summary with its length, SHA-256 and excerpt. A receipt of exactly 8 MiB is kept byte for byte, and one byte more is summarized. Excerpt cases cover two-, three- and four-byte UTF-8; control, quote, backslash and newline escapes; and invalid, overlong and surrogate sequences. Excerpts are measured against the serializer itself and are never split mid-character. Other cases are giant nested profile and drain metadata, 1.1 million nested integers, non-string fields, a giant key, a top-level string, an oversized passing report (never reported as passed), the last-resort summary and bounded exception text. Normal receipts stay byte-identical: the initial report, every failure case and the complete passing report.
- The complete four-phase plan on the executing fake.

The script then compiles the unchanged Windows entry with a test-only POSIX receipt stub ([windows stub](../ChandraNative/runtime/vision_dispatch_calibration_windows_stub.h), [harness](../ChandraNative/runtime/vision_dispatch_calibration_entry_harness.cpp)). It runs the entry's inactive plan with no options, with one pin and with all four valid options. It runs twenty-four argument, pin and path refusals before any receipt; these include both review command lines, which now exit 1 without printing a plan or dispatching.
