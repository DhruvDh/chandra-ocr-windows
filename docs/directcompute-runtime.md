# DirectCompute runtime source and qualification

The native target is Chandra OCR 2 inference in C++ and HLSL through D3D11, developed inside the Const-me/Whisper fork. NorthStone's AMD Radeon RX 7900 XTX endpoint supplies the primary complete-model/OCR and sustained-throughput reference. Independent CPU higher precision operator calculations diagnose numerical error on identical operands and carried state. The historical Intel XPU endpoint and earlier standalone D3D11 primitives remain useful evidence at their original scope; neither establishes a complete native graph. XPU and OpenVINO performance work are outside this continuation.

## Closed original tiny observations

The [October 6 checkpoint](../benchmarks/evidence/directcompute-2026-10-06.json) records two normal, uncapped original tiny runs through caller EOS. Build07’s readback-fixed baseline completed 395 tokens in 616.094 seconds; Build08’s opt-in ordered B1 GEMV completed the same 395 IDs and byte-identical scalar journal in 358.750 seconds. Cached decode/readback took 533.565 and 279.396 seconds respectively. These are one sequential cold point per route with image preparation excluded; there is no sustained-concurrency throughput claim. Both points closed their finite Jobs, retired tracked buffers to zero and restored the ordinary worker cold. Six OCR block contents match the retained CPU first turn, while four geometry coordinates differ by at most two normalized units with no accepted tolerance. Complete trained vectors, AMD/exact-client acceptance, broader corpus, native HTTP serving and the throughput plateau remain open.

The [readback guide](directcompute-readback-wait.md) explains bounded retry of the same staging Map without replay. The [GEMV guide](directcompute-gemv-candidate.md) explains the immutable opt-in selector, ordered arithmetic and correctness-checked calibration. Both are reviewed experimental source; native service deployment remains separate. Build09 also compiles the optional layer/logit recorder described below. The [October 5 checkpoint](../benchmarks/evidence/directcompute-2026-10-05.json) retains the earlier short diagnostic and failed page unchanged.

## Source boundary

[api.h](../ChandraNative/runtime/api.h) defines `Device`, `Buffer`, `Weight`, `ModelWeights` and shared embedding, linear, normalization and elementwise operations. [device.cpp](../ChandraNative/runtime/device.cpp) uses an explicitly identified A770 D3D11 device and rejects foreign-device buffers, aliased SRV/UAV bindings and cross-thread use. It retains buffers referenced by queued commands until an event-query drain completes; staging readback drains before mapping. Its tracked buffer limits are source guards, not observed driver-memory fit or proof of safe end-to-end execution. The AMD machine is the reference endpoint; the current native device selector is not an AMD DirectCompute implementation.

Weights remain packed BF16. Activations use R32 storage with explicit BF16 round-to-nearest-even boundaries; recurrent state and reductions use FP32. [operators.cpp](../ChandraNative/runtime/operators.cpp) and [runtime HLSL](../ChandraNative/shaders/runtime) make those casts and arithmetic visible. Storage format alone does not qualify numerical equivalence. A native implementation must preserve the pinned graph's learned-scale conventions, nonlinear operations, accumulation and return casts, and compare them with a CPU higher precision reference.

[model_weights.cpp](../ChandraNative/runtime/model_weights.cpp) authenticates the exact pinned config and 10,591,220,088-byte safetensors file, validates all 739 original tensor names/shapes/dtypes and accounts for complete, nonoverlapping payload ranges. It hashes the payload once, compares embedding and output-head bytes before sharing storage, uses read-only file mappings and uploads shards of at most 128 MiB under a weight budget of at most 12 GiB. Unused MTP tensors remain authenticated but are not uploaded for the ordinary inference graph. [model_weights_fixture_test.cpp](../ChandraNative/runtime/model_weights_fixture_test.cpp) exercises parser, overflow, malformed-range and shard-plan cases without loading the model or creating a device. Parser/source checks do not prove successful actual import, model-memory fit or inference.

[text_model.h](../ChandraNative/runtime/text_model.h) and [text_model.cpp](../ChandraNative/runtime/text_model.cpp) define a B1, 32-layer text graph with 24 recurrent layers and eight full-attention layers. Source includes projections, causal convolution, learned decay/beta preparation, Q/K normalization, recurrence, gated norm, M-RoPE, KV caching, attention, MLP and output projection. `TextRequest` owns its convolution, recurrent and attention caches; failed or retired requests cannot resume. Prefill processes tiles of at most 64 tokens, and decode advances one supplied token. The connected [inference CLI](../ChandraNative/runtime/inference.cpp) consumes these APIs in a complete source generation path; trained full-model numerical acceptance remains pending.

[vision_model.h](../ChandraNative/runtime/vision_model.h) defines original processor patch/grid inputs, geometry/resource forecasts, a first-block diagnostic and a complete-forward API. [vision_model.cpp](../ChandraNative/runtime/vision_model.cpp) and [vision HLSL](../ChandraNative/shaders/runtime) implement patch embedding, positions, rotary transforms, tiled attention, all blocks and merger. The connected CLI now calls complete vision forward, text embedding, ordered vision-to-text merge, prefill and cached greedy decode. Build06 compiled this integration and its shaders; the later closed tiny points completed caller-EOS generation. Trained vision outputs, merged embeddings and full text histories still require numerical comparison. The native endpoint adapter and complete OCR qualification remain separate work.

## Prepared inputs and connected CLI

[prepare_input.py](../scripts/native/prepare_input.py) packages an existing pinned CPU processor export and frozen public corpus using Python's standard library. It authenticates the report, exact profile, image/prompt and tensor hashes, installed position/caller source bytes and generation/tokenizer configs. It copies the original processor tensors and derives the three-axis positions, text positions and RoPE delta for the source's single-image, unpadded B1 specialization. The caller-derived stop IDs are 248044 and 248046. Packaging uses an exclusive fresh directory, a 128 MiB output ceiling and one original 30-second deadline; it does not import Torch, rerun processing, normalize pixels or execute inference.

For example, select the retained export's actual profile and pass absolute owner-selected paths and its exact SHA-256. This command prepares a tiny public input; it grants no device execution authority.

```bash
python scripts/native/prepare_input.py \
  --processor-report "$PROCESSOR_REPORT" --report-sha256 "$REPORT_SHA256" \
  --corpus "$PUBLIC_CORPUS" --prompt "$PROMPT_FILE" \
  --rope-source "$PINNED_MODELING_SOURCE" --caller-source "$PINNED_CHANDRA_CALLER" \
  --generation-config "$GENERATION_CONFIG" --tokenizer-config "$TOKENIZER_CONFIG" \
  --fixture tiny --profile northstone-serving --output "$FRESH_INPUT_DIRECTORY"
```

The package records that positions are source-derived, not captured AMD internal tensors, and that exact AMD producer EOS token IDs are unavailable. Its pixel check compares the original corpus/export commitments without decoding the PNG again. The currently retained CPU exports do not supply the four exact recorded 1,624 × 2,100 CLI request tensors; the representative serving-profile export cannot replace them because it also has 3,617 tokens. Input packaging alone claims no AMD tensor equality, native numerical qualification, OCR acceptance or speedup.

[inference.cpp](../ChandraNative/runtime/inference.cpp) requires exactly one explicit mode, `--forecast` or `--execute`, with absolute model, shader, input-manifest and fresh output paths, the input manifest's SHA-256, and the selected PCI/LUID. It authenticates typed raw tensors, original patch/grid geometry, ordered image-token rows, caller stop extraction, three-axis positions and finite pixels before creating a device. The prompt and positions must retain the entire normal output allowance; there is no implicit truncation. These Windows CMD examples use owner-supplied variables; `CHANDRA_SHADER_ROOT` names the `ChandraNative/shaders` directory.

```bat
chandra-inference.exe --forecast --model-dir "%CHANDRA_MODEL_DIR%" --shader-root "%CHANDRA_SHADER_ROOT%" --input-manifest "%CHANDRA_INPUT_MANIFEST%" --input-sha256 "%CHANDRA_INPUT_SHA256%" --output-dir "%CHANDRA_FRESH_FORECAST_DIR%" --pci "%CHANDRA_PCI%" --luid "%CHANDRA_LUID%"
chandra-inference.exe --execute --model-dir "%CHANDRA_MODEL_DIR%" --shader-root "%CHANDRA_SHADER_ROOT%" --input-manifest "%CHANDRA_INPUT_MANIFEST%" --input-sha256 "%CHANDRA_INPUT_SHA256%" --output-dir "%CHANDRA_FRESH_RUN_DIR%" --pci "%CHANDRA_PCI%" --luid "%CHANDRA_LUID%"
```

Forecast authenticates and reads the bounded raw input payload on the CPU, creates no D3D11 device and uploads no model. Its `result.json` reports vision geometry/workspace estimates, input and prompt embedding bytes, 1,127,219,200 bytes of source text-request caches and the at-most-12 GiB weight upload budget. The inference reader accepts at most 256 MiB of raw tensors; this is distinct from the packager's 128 MiB output ceiling. Estimates are not observed live driver-memory fit or execution acceptance; `source_forecast_completed` can be true while `passed`, full-graph/OCR qualification and performance flags remain false.

Explicit execution authenticates and uploads the complete ordinary graph, runs vision and merged text prefill, then checks all 248,320 FP32 logits for finiteness before each first-index argmax token. It retains `generated-tokens.jsonl`, complete token history, producer stop evidence, phases, memory observations and retirement/drain results in `result.json`; failure cannot replay a request. An optional positive `--diagnostic-token-cap` below 12,384 declares a short diagnostic, not complete page acceptance. The CLI emits token IDs rather than detokenized OCR HTML and is not an HTTP endpoint. Its successful `passed` scope is finite token production and owned-buffer retirement; the full-graph, OCR and performance qualification flags remain false. External Job, absolute clocks, service/resource ownership and actual process closure must still be supplied by the admitting owner.

## Bounded numerical diagnostics

[diagnostics.h](../ChandraNative/runtime/diagnostics.h) and [diagnostics.cpp](../ChandraNative/runtime/diagnostics.cpp) add an optional, portable dump recorder for locating a trained-model discrepancy before throughput work. It reads existing completed values through borrowed observers: the existing vision observer names `patch_embedding`, `position_added`, `blocks.N.output` and `pooler_output`, and a new optional `TextObserver` on `TextModel::prefill`/`advance` that reports each layer output, GDN conv/recurrent state, per-tile final norm and last-row logits after the graph's own drain, with the absolute causal row, call tile, token, three position axes and observed cache length. Observers run synchronously on the Device thread, never write, retain or dispatch, and fire inside the existing request `try`, so an observer or dump failure poisons and retires the request exactly like a graph failure. Every text observation, selected or not, first passes through the recorder's request-call state machine, which appends the call's consumed rows to a canonical prefix exactly once per prefill or decode call and refuses a callback that skips, repeats or contradicts its call. Without `--diagnostic-dump` the observers are empty and the graph issues the same allocations, dispatches, drains, readbacks and releases as the predecessor; no diagnostic file, readback or source hashing occurs.

`--diagnostic-dump` works with `--forecast` (plan and byte forecast only) or `--execute`. Safe defaults capture patch rows 0 and last, merged rows 0 and last, prompt rows 0, first image, last image and last, all 24 vision blocks and 32 text layers, the merged embedding and final norm for those rows, the complete first-position 248,320-value logits, and decode steps 0–7 with all layer outputs, final norm and complete logits; decode step d consumes generated token d and produces generated index d+1, so the defaults cover the first nine generated IDs. For the prepared tiny input geometry, with four distinct default prompt rows, this is 463 records and 13,268,992 payload bytes; a `--diagnostic-token-cap` below 9 shortens the default decode steps instead of requesting unreachable ones. An optional strict `--diagnostic-plan` JSON file, bound by `--diagnostic-plan-sha256`, uses schema `chandra.directcompute.diagnostic-plan.v1` with optional `byte_limit` and sections `vision` (`rows`, `blocks`, `patch_embedding`, `position_added`), `merger` (`rows`), `embedding` (`rows`), `prefill` (`rows`, `layers`, `final_norm`, `logits`), `decode` (`steps`, `layers`, `final_norm`, `logits`) and `gdn_state` (explicit `layer`, `conv`, `recurrent_heads`, `cache_lengths`). Unknown keys, duplicates, out-of-range rows, full-attention state layers, state lengths other than a completed 64-row prefill tile or reachable decode step, more than 64 rows or decode steps per selection, 4,096 records, the byte limit (default 64 MiB, maximum 256 MiB) or 8 GiB of whole-buffer staging readback are refused after input authentication and before any output directory, Device or model work. Nothing is truncated. The resolved plan written to the forecast and to the dump lists every planned record identity under `forecast.keys`; the SHA-256 of its compact, key-sorted JSON is the dump's plan commitment.

```bat
chandra-inference.exe --execute --model-dir "%CHANDRA_MODEL_DIR%" --shader-root "%CHANDRA_SHADER_ROOT%" --input-manifest "%CHANDRA_INPUT_MANIFEST%" --input-sha256 "%CHANDRA_INPUT_SHA256%" --output-dir "%CHANDRA_FRESH_RUN_DIR%" --pci "%CHANDRA_PCI%" --luid "%CHANDRA_LUID%" --diagnostic-token-cap 9 --diagnostic-dump
chandra-inference.exe --forecast --model-dir "%CHANDRA_MODEL_DIR%" --shader-root "%CHANDRA_SHADER_ROOT%" --input-manifest "%CHANDRA_INPUT_MANIFEST%" --input-sha256 "%CHANDRA_INPUT_SHA256%" --output-dir "%CHANDRA_FRESH_FORECAST_DIR%" --pci "%CHANDRA_PCI%" --luid "%CHANDRA_LUID%" --diagnostic-dump --diagnostic-plan "%CHANDRA_DIAGNOSTIC_PLAN%" --diagnostic-plan-sha256 "%CHANDRA_DIAGNOSTIC_PLAN_SHA256%"
```

```json
{"schema": "chandra.directcompute.diagnostic-plan.v1", "prefill": {"rows": [63, 64, 800], "layers": "all"},
 "decode": {"steps": [0, 1, 2]}, "gdn_state": [{"layer": 0, "conv": true, "recurrent_heads": [0], "cache_lengths": [64, 801]}]}
```

Execution creates `diagnostics/` inside the fresh output directory and writes `progress.jsonl` (schema `chandra.directcompute.diagnostic-progress.v2`) incrementally: a plan line with the resolved plan and its SHA-256, model revision, input-manifest SHA-256, the producer's executable and shader-tree SHA-256 and the consumed-prefix declaration (`chandra.directcompute.consumed-prefix.v1` with the prompt row count); a model line with the authenticated safetensors/config hashes and device identity; `boundary` lines for completed phases with the record and payload counts so far; `conditioning` lines that append consumed request rows `[token_id, t, h, w]` contiguously from row 0, each with the running prefix SHA-256, written before the first record that needs them and once more before the terminal line for rows consumed after the last selected record; a `record_started` line, an exclusively created raw little-endian FP32 payload and then a `record` line (schema `chandra.directcompute.diagnostic-record.v2`) for every selected row; and a terminal `finished` line after success, failure or retirement. Each record states stage, text layer and kind or vision block, phase, decode step, logical shape, its single selected row (or `all` for conv state), payload shape, whether it is the complete tensor, BF16 boundary policy or FP32 state, byte count, SHA-256, observed nonfinite/non-BF16 counts, commitments, coordinates, producer `cache` provenance and, for causal text stages, `conditioning: {prefix_rows, prefix_sha256}`. The terminal line states `run_status` (`completed` with a null error, or `failed` with a message), `dump_complete`, planned and written record counts, the sorted missing record keys, the started but unwritten record, payload and readback totals, and `consumed_rows` with `consumed_prefix_sha256`; a dump is complete only when the run completed and every planned record was written. A started record without its `record` line, a missing terminal line or unreached planned records, including decode steps after an early stop token, leave the dump incomplete; every record and dump stays `qualified: false`. Select an output directory under ignored `results/` or `.local/`; files inherit that directory's access control and `*.f32`/`*.f64` payloads are ignored by Git.

The consumed-prefix commitment binds each text value to its complete conditioning rather than to the current token or the producer's tiling. The canonical stream is the UTF-8 text `chandra.directcompute.consumed-prefix.v1\ninput_manifest_sha256 <hex>\nprompt_rows <P>\n` followed by one `<absolute_row> <token_id> <t> <h> <w>\n` line per consumed row in order, with prompt rows taken from the authenticated input and generated rows from the token and M-RoPE coordinate each decode call actually consumed; `prefix_sha256(n)` is the SHA-256 of the header and the first n row lines. A layer output, final norm or logits row at absolute row r commits to n = r+1; GDN conv/recurrent state after cache length L commits to n = L, with `coordinates.last_absolute_row` L-1 and `last_position` that row's position. Decode step d consumes absolute row P+d, so its records commit to n = P+d+1, and an earlier divergent token changes every later commitment even where the current token coincides. Semantic coordinates are `absolute_row`, `token_id`, `position`, `source`, `last_absolute_row`, `last_position` and the vision/merger row fields. The record `cache` object (completed cache length after the call or tile, request rows before the call, call first row and row count) and the coordinates `call_row`, `chunk_index` and `chunk_row` are producer provenance only, so a monolithic CPU prefill and the native 64-row tiles join on the same causal row or carried state. Joins do not cross phases: a native decode-step value pairs only with a reference value for the same decode step, not with a teacher-forced prefill row.

[compare_diagnostics.py](../scripts/native/compare_diagnostics.py) uses only the Python standard library. It refuses incompatible model revision, safetensors/config or input-manifest commitments, version-1 or malformed dumps, symlinked or orphaned payloads and unsafe names, and unfinished, failed or incomplete dumps unless `--allow-incomplete` is explicit. On load it recomputes the plan SHA-256, requires `forecast.keys` to be sorted, unique and equal to the forecast count and, for a native plan, exactly the identities its resolved selections enumerate; re-derives every record key from its identity fields; re-hashes every payload and recomputes its observed counts; rebuilds the consumed-prefix stream from the conditioning lines and requires every causal text record's prefix SHA-256, phase, decode step, decode metadata, causal row or state endpoint, token and position to agree with the row it names; and requires the terminal line's status, error, completeness, planned, written, missing and incomplete records, payload and readback totals and consumed prefix to agree with the plan and parsed progress, refusing any contradiction even with `--allow-incomplete`. A record declaring a BF16 boundary is valid only if every finite value is exactly BF16 representable, checked for each producer independently of the other producer and of any tolerance. Records pair by stage, layer/block, phase, decode step, state cache length and selected row; differing shapes, decode metadata, semantic coordinates or consumed prefixes make a pair incomparable, an invalid reference boundary makes it incomparable, and an invalid candidate boundary yields `invalid_candidate` whatever tolerances were supplied while its metrics are still reported from the unrounded payload. It reports finite status, maximum absolute and relative error, RMSE, cosine when both norms are nonzero, exact and BF16 ULP agreement where both producers declare valid BF16 boundaries, and for complete vocabulary rows the first-index argmax, top margin, cross ranks, top-five overlap and whether the reference margin exceeds twice the maximum absolute error. It also lists each producer's policy violations and the first consumed row, and generated index, at which the two histories diverge. Tolerances (`--max-abs`, `--max-rel`, `--max-rmse`, `--min-cosine`, `--max-bf16-ulp`, `--require-argmax-match`, per-stage `--stage-tolerance`) must be supplied by the caller; otherwise the verdict is `no_verdict`. Exit codes are 0 within tolerance, 1 outside tolerance, incomparable or invalid candidate, 2 refused and 3 no verdict or an incomplete dump. `write_dump` emits the same format and terminal invariants for a retained CPU FP32/FP64 reference produced from the identical prepared input: it takes the producer's actual consumed rows and prompt length, derives each causal record's prefix commitment from them and refuses records whose prefix those rows do not cover, while `planned_keys` and `run_completed=False` express an early stop or failure. `cpu_oracle_agreement` can be true only when every candidate record is within tolerance, both dumps are complete, neither has a policy violation and the reference producer kind starts with `cpu_`; `amd_ocr_qualified` and `native_numerically_qualified` are always false because primary qualification remains complete OCR against the NorthStone AMD endpoint.

```bash
python3 -I scripts/native/compare_diagnostics.py "$NATIVE_RUN/diagnostics" "$CPU_REFERENCE_DUMP" --max-bf16-ulp 1 --require-argmax-match --output "$FRESH_REPORT"
python3 -I tests/native/test_compare_diagnostics.py
python3 -I tests/native/test_native_diagnostics.py
```

The comparator then authenticates complete 265-record, sparse 14-record, early-stop and failed-record native dumps, joins the tiled native records with a monolithic float64 reference, and marks the sparse decode records incomparable against a reference whose step-0 token differs. ## Public dispatch calibration

[dispatch_calibration.cpp](../ChandraNative/runtime/dispatch_calibration.cpp) provides a model-free, public dyadic GEMM calibration for the native linear shader. It uses input width 9,216, output width 1,024 and ordered batch-row phases 1, 16 and 32, with one unrounded FP32 and one BF16-rounded dispatch per phase. Independent CPU double calculations precede GPU timing; complete output storage words must match exactly. The source tensor/readback forecast is 20,447,232 bytes, below its 256 MiB allowance. This probes dispatch behavior and exact synthetic arithmetic, not trained operators or page throughput.

The executable is inactive without `--execute`. Explicit execution requires the absolute shader root, fresh result file and exact PCI/LUID; the owner must supply the declared external Job, 256 MiB process commit cap, one core at below-normal priority and current resource/closure admission. Its original source deadline is 120 seconds. Each completed, nondisjoint D3D11 timestamp window must contain exactly the two expected linear dispatches, with finite nonnegative durations strictly below 100 ms, before admitting a larger phase. A mismatch or breach stops without rerun, retains the result and requires owned closure; calibration does not reset the deadline or establish end-to-end performance.

```bat
dispatch-calibration.exe --execute --shader-root "%CHANDRA_SHADER_ROOT%" --pci "%CHANDRA_PCI%" --luid "%CHANDRA_LUID%" --output "%CHANDRA_FRESH_CALIBRATION_FILE%"
```

## Qualification ladder

First authenticate source, shader, runtime, adapter and model bindings, then reject malformed imports and invalid shapes before work. Check native operators against independently evaluated CPU higher precision outputs on the same prepared operands, preserving exact BF16 inputs/casts and FP32 state. The existing [C++ recurrence oracle](../ChandraNative/oracle.h) evaluates independent FP32 and double carries; [operator_fixture.cpp](../ChandraNative/runtime/operator_fixture.cpp) adds synthetic projection, normalization, BF16 cast, recurrence and attention checks. Operator01 passed 13 selected tiny synthetic checks, including continuous/split recurrence and unrelated state isolation. Extend that coverage to extremes, nonfinite refusal, trained operands and the original graph's complete semantics. Local error screens must keep their declared scope rather than becoming a claimed full-model error proof.

Next compare complete recurrent and attention layers, continuously carried state and all checkpoints; cover prefill/decode equivalence, causal masks, M-RoPE, chunk boundaries, reset and request isolation. Check vision patch embedding, positions, every block and merger against the identical processor tensors before admitting merged text/vision embeddings. Then retain every full-vocabulary logit row and cache/state association for complete conditional histories, followed by free generation through genuine EOS. [The existing numerical workflow](../verification/README.md) provides historical export/comparison routes and failed examples; its CPU FP32 graph is distinct from the higher precision operator oracle.

Full OCR qualification requires the complete original pages, ordered prose, equations, table row/column associations, protected markup, geometry, metadata and stop/token evidence. Human-authored expectations and the AMD endpoint complement the operator oracle; matching a few tokens or a reference transcription alone is insufficient. Exercise repeated/interleaved requests, unequal EOS lengths, cancellation with survivors, failure, actual drain, allocator/process closure and restoration before native serving. Preserve all earlier failed experiments and avoid replaying a submitted request. The [historical evidence index](../benchmarks/evidence/hillclimb-2026-10-04.json) remains unchanged.

## Build and throughput boundary

[runtime/build.cmd](../ChandraNative/runtime/build.cmd) describes a Windows source build into an explicit output directory using MSVC C++17 and strict floating-point flags. It compiles the device, shared operators, importer, text and vision graph and the optional diagnostic recorder into `chandra-runtime.lib`, and produces `operator-fixture.exe`, `dispatch-calibration.exe`, `chandra-inference.exe` and `shader-compile.exe`. [shader_compile.cpp](../ChandraNative/runtime/shader_compile.cpp) compiles all runtime HLSL on the CPU without creating a GPU device. Build06 completed this connected build successfully in 69.016 seconds with no native GPU execution. The separate operator01 run passed the 13 synthetic checks described above. Those Build06/operator observations alone establish no trained import, OCR or throughput acceptance. The later Build07/08 closed tiny runs supply their separately stated trained import, caller-EOS output and sampled resource/closure evidence; broader numerical, OCR and sustained-throughput qualification remain open. The older [primitive build and evidence guide](../ChandraNative/README.md) retains its separate synthetic and single-layer results without promoting them to this graph.

```bat
ChandraNative\runtime\build.cmd "%CHANDRA_FRESH_BUILD_DIRECTORY%"
```

After the complete native path passes the correctness and lifecycle ladder, measure correctly completed pages per sustained interval against the AMD 7900 XTX reference. Include fresh page decoding/preparation, transfers, vision, embedding merge, text prefill, cached decode and output completion. The current CLI times one request from preprepared tensors and explicitly excludes original image decoding and processor work; that interval alone cannot establish end-to-end page throughput. Separate loading, compilation, prime and warmup from measured work; disclose repeated pixels or any cache/precompute reuse. Sweep safe concurrency, repeat results and measure adjacent points to locate the useful plateau, retaining complete outputs and observed memory/drain/closure evidence. Primitive bandwidth, dispatch timing, shader counts and theoretical roofs may guide implementation, but cannot be reported as measured native page throughput. Qualified inference-engine speedup remains 0%, and no new native full-model or throughput qualification is claimed by this source documentation.
