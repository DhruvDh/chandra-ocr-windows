# Maintained llama-server adapter candidate

This package is an opt-in, unpromoted integration candidate for llama.cpp b11429 (`d81235049384534c167caea52b85a694f6103d14`) on Windows Vulkan. The explicit `llama` CLI mode is available in source; nothing is installed, enabled, or deployed by importing the package or adding this mode. Existing service defaults are unchanged. Authenticated configuration selects exactly 1, 2 or 4 concurrent slots, with a complete 16384-token context per slot, batch/ubatch 128 and unchanged 12384-token maximum output. Multi-slot profiles explicitly disable unified KV storage and allocate total context as 16384 times the slot count; startup verifies every reported slot context. The engine uses the evaluated Q8_0 text weights and BF16 projector/cache profile only when an operator supplies those exact authenticated files. Q8_0 is integer weight quantization, not native FP8 arithmetic. Numerical qualification and sustained performance remain independent promotion requirements.

`LlamaBackend(config)` implements the existing `Backend` protocol, and `create_llama_app(backend, ...)` adds worker retirement to the existing service lifespan. Health and model listings never authenticate model files, start a process, or load a device. The first validated request uses the existing `runtime.sycl.prepare_request` CPU path, holds and authenticates the executable/DLL inventory, text weights, projector and standalone template, and starts one private loopback worker using `WindowsJobTransport`. A random API key and model alias identify that worker; the client disables environment proxies and redirects. Concurrent callers share serialized startup. Successful requests leave the worker resident for the existing idle-unload policy. No submitted generation is replayed, rerouted, or silently shortened.

The private HTTP client preflights the identical prepared chat body through b11429's multimodal `/v1/chat/completions/input_tokens` endpoint and requires `prompt_tokens + requested_max_tokens < 16384`. This endpoint tokenizes placeholder image input and creates no completion task. Each generation receives one exclusive, bounded `id_slot` and `n=1`; the adapter never forwards a caller-supplied slot. Generation uses deterministic sampling, the requested `top_p` and output allowance, disabled thinking, disabled prompt/cache reuse, and streamed content plus truthful final usage. The final SSE is not a release barrier in this pin: `send_final_response()` precedes `slot.release()` in [server-context.cpp](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/tools/server/server-context.cpp#L4222). Before returning final metadata, a new authenticated `/slots` query after this request's DONE must report its reserved slot idle; other slots may remain busy. The snapshot is not used as a pre-submission FIFO barrier, and the internal `id_task` is not mistaken for the HTTP completion ID. The pinned server silently wraps invalid `id_slot` values, which is why the adapter and startup inventory both enforce the exact range.

A malformed response, cancellation, deadline, guard trip or abandoned unfinished generator retires the whole owned Job and joins both output drains before any affected call returns capacity. Unfinished peers receive failures and are never replayed; their existing private client and reservations remain tied to the retiring worker. Input preparation or context refusal before a generation POST releases only that request's reservation because those operations allocate no completion task. New demand cannot replace a stopping worker until all of its affected calls have returned. Unconfirmed cleanup retains ownership and blocks capacity; health remains readable. A fault latches admission closed until the adapter is restarted. Ordinary cancellation or a prelaunch headroom refusal permits a later new request after confirmed retirement. Completion and subsequent cancellation of an already successful call do not abort its still-running peers.

The fixed process/Job caps are 10.5/10.75 GiB, below-normal priority and one CPU, enforced by the existing Windows transport. Default startup forecasts are 6 GiB additional physical and 11 GiB additional machine-wide commit; authenticated operator configuration may set a different forecast based on measured evidence. Both before authentication and immediately before launch, the forecast must leave strictly more than 4 GiB in both observations. A 0.1-second monitor retains the same fixed 4 GiB live floor throughout startup, generation and idle residence. Physical availability comes from `GlobalMemoryStatusEx`; machine-wide available commit comes from `K32GetPerformanceInfo` as `(CommitLimit - CommitTotal) * PageSize`. The observation labels this `system_commit_limit_minus_total` and separately retains the caller-constrained `ullAvailPageFile` as `reported_process_commit`, which does not control admission. This matters when the adapter itself inherits a limiting outer Job. The [Microsoft field contract](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/ns-sysinfoapi-memorystatusex) distinguishes these metrics; the existing forecast is a conditional experiment allowance, not a calibrated prediction of the newly explicit system counter. The sampled floor and Job caps do not promise protection from every foreign allocation spike.

Configuration is a SHA-256-authenticated JSON object, loaded by `load_config(path, expected_sha256)`. Required fields are `activate` (exactly `evaluate-llama-b11429-vulkan`), `runtime_dir`, `runtime_files`, `model`, `projector`, `template`, `device_index`, `worker_cpu`, `startup_seconds`, `request_seconds`, `max_image_pixels`, and `parallel_requests` (integer 1, 2 or 4). Each file identity has absolute `path`, exact `size`, and lowercase `sha256`; `runtime_files` must list every adjacent `.exe` and `.dll`, including `llama-server.exe`. The directory is an operator-provisioned private runtime, not an installation target. Symlink/reparse inputs and unexpected executable/DLL inventory are refused; held files deny replacement while the worker owns them. `device_index` sets the explicit Vulkan visibility index; the visible text and vision device is `Vulkan0`. Optional `admission_physical_bytes` and `admission_commit_bytes` change only admission forecasts; each deployed concurrency profile still needs its measured startup allowance. There is no supplied runnable configuration, automatic discovery, backend fallback or automatic precision selection.

The adapter uses only the existing HTTP/service dependencies and the pinned CPU preprocessing dependencies. Tests under `tests/llama` use fake owned workers and in-memory HTTP transports, never real sockets, Windows processes or model calls. Literal `codex --no-daemon review` with Sol 6.1 xhigh found a retirement-time fault that could permit fresh admission; it was fixed by latching the confirmed retirement receipt's fault before releasing capacity, with typed expected startup cancellation remaining retryable. Later literal reviews cleared the opt-in CLI, finite qualification recipe, nested-Job commit correction and idle scheduling fix. The current combined regression passed 82 tests and 44 subtests in 4.15 seconds across `tests/llama`, `tests/service/test_launcher.py`, `tests/service/test_parallel_capacity.py` and `tests/service/test_service.py`, using one CPU, a 1 GiB address-space ceiling and 45-second CPU/wall limits. A colliding test module basename was corrected by renaming the unchanged reviewed llama launcher test to `test_llama_launcher.py`. Coverage includes overlapping C2/C4 requests, shared startup, independent slot reuse, complete-context validation, canceled peers retaining capacity through retirement, memory trips, differing process/system commit observations, passive health/model polling through idle unload, continuous backlog retaining execution permits, no replay and unchanged default service behavior. These checks establish tested fake lifecycle behavior, not Windows runtime qualification. Deployment still requires the exact runtime's Windows startup, streamed response, disconnect/cancel, idle unload, shutdown and memory-trip behavior to be exercised under the owned experiment launcher, followed by the separate correctness/performance decision.

The CLI follows the existing positional mode convention: `python -m chandra_service llama --llama-config ABSOLUTE_PATH --llama-config-sha256 SHA256 --host 127.0.0.1 --port 18004 --queue-limit 3`. Both configuration arguments are mandatory and are refused in other modes. Llama mode refuses unrelated model/configuration inputs and nondefault XPU/conditioning overrides; its model, device, image admission and context limits come exclusively from the authenticated configuration. It verifies that Windows Job APIs are available before creating a listener, then uses `create_llama_app` for owned shutdown. This capability check creates no Job or GPU allocation. The service accepts bounded integer `parallel_requests` from 1 through 64. Its idle monitor checks for no admitted work and expired activity before acquiring execution permits, then rechecks under the all-slot barrier; it cannot collect slots from a continuous backlog. Cancellation releases any partial barrier acquisition, and the default one-slot behavior remains unchanged. This adapter exposes only its explicit 1/2/4 profiles. `queue_limit` continues to mean total admitted jobs minus one, so admitting all four engine slots requires at least `queue_limit=3`; it is not an independent execution-concurrency setting. Health and model listings neither wake the engine nor renew its inference idle timer.
