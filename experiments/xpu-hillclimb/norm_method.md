# Cached normalization gains

Gain-only normalization passed exact cached numerical comparison and complete OCR on five frozen synthetic pages. Two of five planned timing pairs completed, but memory qualification remains unresolved and further GPU trials are held. No optimized implementation has been deployed. Native fused normalization failed the full-trajectory numerical gate and is set aside. The [evidence index](../../benchmarks/evidence/hillclimb-2026-10-04.json) links the retained receipts; the [numerical protocol](../../verification/hillclimb-numerical-gates.md) defines the acceptance boundaries.

## The change

The pinned graph has 81 zero-centered text norms: two norms in each of 32 decoder layers, Q/K norms in eight full-attention layers, and the final text norm. Each normally computes `1.0 + weight.float()` during every forward. [norm_candidate.py](norm_candidate.py) computes that exact FP32 gain once for each frozen BF16 weight, then keeps the original FP32 normalization, separate gain multiplication and final BF16 cast. Gated norms and vision operators remain unchanged.

The gains occupy 681,984 bytes before allocator rounding. Removing the repeated weight upcast and gain addition should eliminate about 162 small operator launches per cached token. This is a source-based forecast, not a measured kernel reduction or speedup. The baseline trace found approximately 2,740 kernels per decoded token, which made this a useful candidate to measure.

The experimental scope checks the pinned graph and Torch version, exact norm type, eval state, BF16 XPU inputs, input width and unchanged weight identity/version. It records every interception and restores each original forward afterward. The prepared [production module](../../runtime/waystone/norm_gain.py) gives the loaded model ownership of those gains and restores per-instance attributes before releasing them. Its `original` rollback selection remains the default until deployment qualification is complete.

## Correctness evidence

The trained capture covered all 81 modules at prefill and first cached decoding: 162 fixtures, each retaining actual inputs, original output, weight, gain and hashes. An independent NumPy FP32 equation oracle, with explicit ties-to-even BF16 rounding, checked gain values exactly. The subsequent gain-only full cached export matched all 395 complete vocabulary rows byte for byte and matched every shape, dtype, finiteness flag and tensor-byte hash in 25,280 cache records. Each norm executed 396 times, including the final uncached diagnostic, and all scoped forwards restored. Its final cached/uncached discrepancy also matched the unchanged hybrid baseline; gain caching did not alter that existing discrepancy.

All five complete OCR cases passed with the normal 12,384-token allowance: tiny and small each produced 395 tokens, representative 397, routes 595 and ledger 526. Each matched its qualified reference's complete HTML, usage, proper stop, ordered content and every bounding box, with zero coordinate difference. The new routes and ledger references also retained generated token IDs, which matched exactly. The older three references did not record historical generated IDs; their exact text, counts, stops and geometry remain the comparison boundary. Across the five candidate requests, 186,948 norm interceptions were verified. Every run restored its scope and unloaded to zero Torch allocated/reserved GPU bytes.

The new routes baseline briefly returned a successful `OpenProcess` handle after its wrapper had reported a clean exit and zero GPU allocations. The sequence stopped. Two later independent probes returned no handle with Windows error 87, establishing current absence; the cause of the earlier observation remains unresolved. A denied CIM query was not counted as evidence. No inference was replayed, and the original observation remains in the retained receipts.

The separately prepared production implementation has now passed CPU replay on all 162 trained fixtures: output bits match ordinary CPU normalization, captured FP32 gains match exactly, and restoration and ownership release pass. Comparing those CPU outputs with the captured XPU outputs gives 30 differing elements among 2,935,296, with maximum absolute difference 0.015625; this describes the CPU/XPU reduction boundary and does not qualify the new implementation on XPU. A small weak-reference test confirms that the production expression releases the converted FP32 input object before gain multiplication, while the reproduced experimental sequence retains it. Neither result measures GPU peak memory. Both CPU processes completed in less than three seconds with peak RSS under 234 MiB. The [prospective production protocol](../../verification/gain-production-protocol.md) identifies the new candidate and its strict allocation gate; the old partial timing result remains held.

## The rejected fused variant

The separate `fused` mode replaces only unweighted FP32 normalization with native XPU `torch.rms_norm`, retaining the separate gain multiplication and BF16 cast. The [PyTorch operator registration](https://github.com/pytorch/pytorch/blob/v2.14.1/aten/src/ATen/native/native_functions.yaml) and [RMSNorm implementation](https://github.com/pytorch/pytorch/blob/v2.14.1/aten/src/ATen/native/layer_norm.cpp) establish the native route; runtime dispatch was checked before execution. No compiler was used.

On 162 trained fixtures, 35 of 2,935,296 output elements differed from original XPU normalization, all during prefill; all 81 first-cached fixtures were exact. The maximum difference was 0.015625. Some fused outputs were closer to the independent CPU equation oracle, but the complete cached trajectory failed the frozen policy at 17 positions: 805, 806, 809, 816, 851, 878, 882, 886, 916, 918, 924, 990, 1165, 1169, 1170, 1173 and 1174. Position 924 also introduced a digit change outside the approved exception set. The maximum total-variation error was 0.458568 versus the baseline's 0.379371, and maximum target log-probability error was 1.188969 versus 0.860880. No fused free OCR or performance run followed.

## Reproduce and measure

Run through the authenticated Windows Job Object channel under an exclusive GPU lease, with the ordinary worker stopped. [norm_export.py](norm_export.py) supplies scoped numerical capture/export; [norm_operator.py](norm_operator.py) replays trained inputs, and [norm_cpu_reference.py](norm_cpu_reference.py) supplies the independent equation oracle. Retain exact source, checkpoint, runtime, processed inputs, policy and output commitments. Numerical capture and export synchronize/copy tensors and must stay outside performance measurements.

[recurrent_run_ocr.py](recurrent_run_ocr.py) also supplies the compiler-free `norm-gain` mode for complete OCR. The separate [paired runner](paired_norm_ocr.py) measures the representative page within one loaded model, warming both variants and alternating their order. Its timer includes input decoding, processor work, H2D transfer, generation, streaming, buffered event logging, thread join and terminal scalar readback. Loading, patch/gain setup, bulk token readback and validation are excluded. Live memory is sampled before leaving the gain scope; post-restoration memory and allocator peaks are retained separately.

The performance decision was frozen before measurement: five pairs in bounded batches of two, one and two, with no optional stopping. Every request must match complete generated IDs, HTML, usage and termination and prove fresh generation state. Promotion requires all five candidate times to be lower, median paired latency reduction of at least 2%, and no material memory increase beyond the gains, whose upper bound is 1 MiB. Allocator granularity must be reported separately. The frozen policy did not define a tolerance for transient allocation beyond those gains; that omission cannot be resolved by inventing a permissive threshold after seeing results.

The first batch completed two pairs: baseline 87.854 seconds versus candidate 84.747 seconds, then 86.933 versus 85.083 seconds. Both matched all 397 generated IDs, complete HTML, usage and proper termination, with fresh generation state and verified norm restoration. The persistent gain allocation was exactly 681,984 bytes and disappeared after restoration. Peak allocated memory increased by 1,241,088 bytes, including 559,104 bytes beyond the gains; measured reserved memory did not increase. The candidate keeps an FP32 input local alive through the final cast, which offers a plausible source-level explanation but does not establish the cause of the measured peak. Independent review left memory qualification unresolved. The remaining three pairs did not run, so the required five-pair performance decision is incomplete and no speedup is promoted.

The batch unloaded to zero Torch allocated/reserved bytes, and its child process was confirmed absent. Experimental GPU work is held while other important work continues; the ordinary qualified endpoint has been restored without loading the model. Any future implementation change needs a separately identified candidate and prospective memory policy, retaining this partial result. A passing complete comparison would still require exact deployed OCR, cancellation recovery, real idle release and correct reload before serving changes are accepted.
