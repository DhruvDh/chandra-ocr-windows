# Offline batch and phase model

Run `python benchmarks/roofline.py` for the retained representative geometry, or `python benchmarks/roofline.py --batch 15` for a hypothetical fifteen-row batch with that same geometry. These commands use only the standard library and sanitized [model assumptions](roofline-inputs.json); they do not import Torch, load weights, contact a service or authorize a GPU allocation. `--inputs` accepts another assumption file with the same schema. The pure `build(model, batch, prefix, patches, completion, vision_segments=None)` function also supports offline analysis.

The JSON separates dense arithmetic estimates, ideal projection-weight traffic, lifetime shape estimates and persistent state storage. Two FLOPs per multiply-add are counted. The sixteen-query-head text projections and vocabulary head require about 8.410 billion projection FLOPs per active decode row. Ideal shared BF16 weight traffic is about 8.410 billion bytes per batch step, independent of batch size; this is an optimistic reuse term, not measured DRAM traffic. Batch size therefore raises ideal projection arithmetic intensity, but does not establish useful throughput or an admissible batch size. Row padding and finished sequences can consume work without completing more pages.

Vision attention squares each segment length within a page, then multiplies by batch size. For example, `python benchmarks/roofline.py --vision-segments 6048,6048` models two equal segments rather than one 12,096-patch segment; it halves the attention arithmetic estimate while leaving projection arithmetic unchanged. It does not claim that the retained representative page uses that segmentation. Never square patches concatenated across independent pages. Text prefill assumes dense eager QK/AV matmuls and one sliced vocabulary position. The softmax pair estimate assumes the scoped BF16-score/FP32-softmax lifetime variant and excludes masks/workspaces.

Per-page FP32 linear recurrent state is 50,331,648 bytes, and stored BF16 K/V is 32,768 bytes per page token. The output exposes state costs for the chosen completion length and the normal 12,384-token allowance. Activations, recurrence arithmetic/traffic, expanded KV heads, concatenation copies, patch embedding/merger, nonlinearities, padding waste, driver memory and allocator fragmentation remain outside this partial model. Total peak process memory and admissible batch size remain null; storage arithmetic is not a memory-admission envelope.

Effective bandwidth, precision-and-shape-compatible compute and ordinary launch time are null. This version does not ingest hardware calibration: it cannot validate that a benchmark measurement supplies a compatible empirical roof. The equation `max(F/C, Q/BW)` needs those roofs and actual traffic before providing a device lower bound; CPU dispatch and synchronization are separate costs. Advertised bandwidth or a different precision's FLOPs/s must not be relabeled as measured workload performance. Sustained correctly completed pages/sec remains null. Source hashes commit the dimension/projection derivation without publishing private paths, tensor pointers or runtime receipts.

The installed one-request Intel worker's client queue concurrency is distinct from this model's true batch size. A separately qualified batch of two is a possible initial correctness experiment, not a permanent ceiling. Search larger safe batches and client concurrency for the useful completed-page plateau only after numerical, complete-output, EOS/padding/state-isolation and resource qualification. The model contains no measured saturation result, speedup or cross-node load-balancing claim.
