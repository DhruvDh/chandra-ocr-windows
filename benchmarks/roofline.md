# Offline native geometry and phase model

Run `python benchmarks/roofline.py` for the default B1 scenario: 3,617 prompt tokens, 12,096 patches and an analytical completion length of 397. The original Zotero page has 1,624×2,100 pixels, with context 16,384 and normal output allowance 12,384. Run `python benchmarks/roofline.py --queue-concurrency 15` to record client demand with the same B1 estimates, or `python benchmarks/roofline.py --batch 15` for hypothetical true model batching. The current native source executes serial B1 with one active and one waiting request; it implements no fifteen-row batch. These stdlib commands use sanitized [model assumptions](roofline-inputs.json), load no model, contact no service and authorize no GPU allocation or queue admission. Completion 397 is a scenario input, not a qualified native page outcome.

`--inputs` accepts `chandra.roofline-inputs.v1`; the output remains `chandra.roofline-estimates.v1`. The pure API is `build(model, batch, prefix, patches, completion, vision_segments=None, *, queue_concurrency=1)`. `scenario.batch` means hypothetical rows in one model invocation; `scenario.client_queue_concurrency` records queue demand. `native_engine` describes serial B1, and `scenario.matches_current_native_model_batch` checks only the row count, without claiming correctness or resource admission. The fixed native cache fields describe the pinned native graph even when another assumption file supplies hypothetical dimensions.

The JSON separates dense arithmetic, ideal projection-weight traffic, lifetime shape estimates and native fixed storage. Two FLOPs per multiply-add are counted. Text projections and the vocabulary head require 8,409,579,520 projection FLOPs per active decode row and occupy 8,409,579,520 bytes of BF16 weights. One ideal shared weight sweep per invocation is independent of hypothetical batch size. Its per-row amortization requires actual engine batching; queued requests do not provide that reuse. `precision_scope` labels BF16 weight storage separately from FP32 KV and recurrent storage, without asserting a compatible shader compute roof.

Native KV occupies 65,536 bytes per page token: eight K/V pairs use four-byte FP32 floats through raw `R32_TYPELESS` views, even when values are BF16-rounded. `capacity_terms.native_request_resident_cache.bytes_per_request` reports the full allocation made by `TextModel::newRequest`: 1,073,741,824 KV bytes for all 16,384 positions, 50,331,648 recurrent-state bytes and 3,145,728 convolution-history bytes, totaling 1,127,219,200 bytes per request. This fixed cache allocation does not shrink with prefix/completion length or grow with client queue demand. Model weights, activations, temporary buffers, driver memory and fragmentation still require separate accounting; total peak process memory and admissible batch size remain null.

`recurrent_plus_final_kv_bytes` and `recurrent_plus_allowance_kv_bytes` describe logical occupied recurrent/KV storage for hypothetical model rows, exclude convolution history and carry `logical_occupied_storage_not_resident_allocation` status. Prefill predicts completion token one; only `G − 1` cached forwards consume generated tokens, so occupied context ends at `P + G − 1`. These terms therefore cannot replace the native fixed allocation in a memory forecast. The [conditional cached-decode scenarios](../docs/roofline-scenarios.md) explain the separate traffic accounting.

`phases.text_prefill.native_chunked_prefill_per_request` describes the native0 source schedule: the original 3,617-token prefix has 57 successive chunks, comprising 56 full 64-token chunks and a 33-token tail. Each chunk visits 7,138,181,120 bytes of distinct text projection weights, followed by one 1,271,398,400-byte vocabulary-head sweep after all chunks. `projection_weight_sweep_bytes` is thus 408,147,722,240 bytes under the conditional one-sweep-per-chunk assumption. The separate `projection_weight_bytes_once` remains the ideal whole-prefix 8,409,579,520-byte sweep. Shader row groups may request operands repeatedly and caches may satisfy requests across groups/chunks; neither number is measured DRAM traffic. `dram_traffic_bytes` remains null.

Vision attention squares each segment within a page, then multiplies by hypothetical batch size. `--vision-segments 6048,6048` halves the attention estimate relative to one 12,096-patch segment while preserving projection work; this does not identify the original page's segmentation. Never square patches concatenated across independent pages. Whole-prefix text attention and the scoped BF16-score/FP32-softmax pair estimate describe an ideal alternate schedule, exclude masks/workspaces and do not predict current native chunked allocation.

`empirical_roofs`, `measured_timing`, `analytical_hardware_ceiling` and sustained correctly completed pages/sec remain unknown. No clock, bandwidth, XMX peak or driver compatibility is assumed. `max(F/C, Q/BW)` requires compatible empirical roofs and actual traffic; CPU dispatch, synchronization and overlap need separate treatment. Source and model-assumption hashes record analytical inputs without qualifying runtime provenance, numerical correctness, observed fit, a throughput plateau or a speedup. Apply the [sustained-throughput method](../docs/sustained-throughput.md) after native correctness and resource qualification.
