# Prospective direct-node throughput runs

The HTTP adapter is prepared capability, not a hardware result. Run its fake-only checks with `.venv/bin/python -m unittest benchmarks.test_throughput_live benchmarks.test_throughput`. The offline core remains useful for scheduling checks. No result here establishes a throughput ceiling, GPU roofline, new corpus encounter, or admissible hardware configuration.

A coordinator must first admit one node and engine configuration, hold hardware ownership, prepare its external resource/identity monitor, and freeze the same endpoint `inputs-v2` corpus order and work count for every concurrency. Warmup is separate and mandatory. Choose enough repeated work to expose sustained behavior; complete-work first-admission-to-client-completion and setup-to-independently-observed-backend-drain rates are both recorded. Resource monitoring and whole-run ownership deadlines belong to the coordinator; this client never releases that ownership. Do not infer engine concurrency from HTTP requests in flight or `pending_or_active`.

Execution requires both `--execute` and a fresh external JSON admission: `python benchmarks/throughput_live.py --execute --direct-url http://NODE:PORT --corpus CORPUS --monitor MONITOR.json --admission ADMISSION.json --output NEW_OUTPUT`. The URL is a single origin, with no automatic/router mode. Only passive `/health` and normal `/v1/chat/completions` requests are available. There are no lifecycle management calls, redirects, environment proxies, POST retries, fallback nodes or replay after ambiguous execution. This prepared adapter requires an already warm, identified worker. Cold start and sleep/wake studies are held; `initial_loaded` must be true and `allow_request_wake` must be false.

Admission uses candidate `direct-node-throughput-live-v1`, `root_live_throughput_lease: true`, a unique safe `lease_id`, `node_id`, exact `direct_url`, fresh `issued_unix` and `expires_unix`, bound `monitor_path`, `expected_worker`, and exact `expected_health` containing backend/model/revision. Bind explicit `health_profile` (`waystone` or `northstone`), `initial_loaded`, `allow_request_wake`, `node_source_sha256`, and `source_sha256` for all five files listed by `SOURCE_FILES`. Freeze `corpus_metadata` returned by `throughput.corpus_work`, `planned_pages`, `repeat`, `warmup_cycles`, `concurrency`, `work_limit`, `request_seconds`, `cell_seconds`, `drain_seconds`, `poll_seconds`, `monitor_max_age_seconds`, `response_bytes`, `max_output_bytes`, and `max_client_bytes`. Lease coverage must include every warmup, measured cell, pre-cell passive health deadline and terminal drain deadline. A conservative forecast of all per-request, watcher, drain and setup witness samples must fit the fixed 10,000-sample cap before HTTP admission; use a coarser admitted polling interval or a smaller frozen run envelope rather than exhausting it during a run. Sources, input/expectation bytes, worst-case raw disk forecast, actual artifact growth including temporary atomic replacements and the client working envelope are checked before or during admission. The external monitor must still enforce actual host/process RSS and GPU resource allowances; a client data-envelope calculation is not an RSS measurement.

The external passive monitor must atomically publish a bounded JSON receipt with matching lease/node/worker/source/model revision, fresh `issued_unix`, and explicit `allow_admission`, `resources_passed`, `abort`. It must also report matching `backend`, `model`, `model_revision` and an actual `health_state`. Its worker identity must come from an independent passive process/engine observation; it is not fabricated from the expected fields. Waystone health must directly match backend/model/revision/loaded state. NorthStone uses the actual gateway status contract without inventing these fields; external runtime evidence binds model/revision instead. Its identified initial worker must be `awake` with explicit `initial_state`; sleep/wake and cold worker launches remain held for a separate capability. If health exposes worker PID/starts, those must also match. Fresh pre-cell health requires a warm, idle, unchanged worker before measured work; monitored state guards continue during requests. An abort, expired lease, stale monitor or mismatched identity blocks new POSTs and invalidates the cell. Transport cancellation terminates local client tasks only; raw partial replies and ambiguous errors are retained, and a separate passive drain check follows. A transient fault stops the sweep and retains ownership uncertainty.

Drain requires a source-supported explicit contract and `drain_contract_source_sha256`. `service-pending-holds-inference` is admissible only when the pinned service keeps pending ownership until its actual inference producer has stopped. `external-engine-metrics` additionally requires bound `engine_metrics_source` and fresh external `engine_telemetry` with that source, exact integer `running` and `waiting` values, and `observed_unix`; both must reach zero along with health pending. This does not discover or guess a metrics endpoint. Missing engine telemetry is recorded as unavailable, never inferred from the gateway queue. Per-phase GPU occupancy remains unavailable; reported engine running/waiting gauges establish scheduler occupancy only. Successful passive drain is a bounded terminal observation, not proof of worker process exit or authority to release another task's GPU lease.

Per-request files bind IDs, request hashes, timings, quality checks, HTTP status, transport attempts and raw replies. Read faults, byte limits and cancellation retain bounded partial bytes with explicit failure; they cannot yield a valid rate. Every admitted normal response uses the unchanged endpoint validator. All warmup and measured-cell failures gate later admissions. The summary is finite-work evidence; steady-state discovery, first-seen corpus testing, node engine telemetry and roofline measurements require their own authorized method and observations.
