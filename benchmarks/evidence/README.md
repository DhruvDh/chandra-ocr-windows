# Measured synthetic acceptance

The [October 3 summary](2026-10-03-summary.json) curates the retained `northstone-01`, `waystone-01`, `recorded-cli-northstone-01` and `recorded-cli-waystone-01` acceptance records. It records observed endpoint and CLI behavior with SHA-256 commitments to 198 retained raw artifacts. The raw records remain in the owner's private task evidence; the commitments identify their exact bytes without publishing private paths, runtime credentials or adapter UUIDs. Independent curation checked every original endpoint receipt inventory, both recording proxies' request and response bytes, decoded request pixels, raw completion stop reasons and counts, and CLI output and stream hashes.

Each endpoint completed one separate representative-page warmup followed by five unprofiled warm requests. All ten measured requests passed the synthetic content checks, returned `stop` and produced 397 completion tokens. NorthStone's median was 11.069389 seconds and Waystone's 85.164285 seconds. These are end-to-end non-streaming request times for one development page; first-token and separate generation times were not measured for those requests. Both original `performance_promotion` flags remain false. They do not establish general document throughput or quality.

Waystone's separate process-cold tiny-page stream took 107.128540 seconds overall and 26.004585 seconds to first token, producing 395 completion tokens with `stop`. This request includes loading and inference; it does not isolate model-load time and uses a different fixture from the warm representative requests. The Waystone integration also recorded passing concurrency and streaming cancellation checks; their individual scope statements remain in the summary.

Both backends passed two-page native and scanned synthetic PDFs through `chandra input.pdf output --method vllm --batch-size 2 --no-html`, with `MAX_VLLM_RETRIES=0`, model alias `chandra` and an explicitly selected backend. Checks cover prose, columns, equations, numerical table associations, page order, metadata and absence of generated HTML files. Recorded CLI elapsed times were 18.168100 seconds native and 17.762884 seconds scanned on NorthStone, versus 270.743183 seconds native and 239.637227 seconds scanned on Waystone. These include the CLI and concurrent two-page request behavior; they are not per-page inference timings.

The initial CLI reports checked content and metadata without raw HTTP stop evidence, so their original `truncation_verified` and `full_ocr_acceptance` flags remain false. The later recording proxy supplies the missing evidence: all four actual requests on each backend map uniquely to the decoded pixels of a frozen page after the installed Chandra scaling operation; all eight actual responses terminate with `stop`. NorthStone completion counts are 556/560 for native pages 0/1 and 556/559 for scanned pages 0/1; Waystone counts are 556/560 and 557/559 respectively. Waystone's native page 1 arrived before page 0, demonstrating why the association uses pixels rather than arrival order. Each association retains both frozen-page and scaled-request pixel hashes.

All original `provenance_verified` flags remain false, and both recording receipts' `remote_runtime_source_identity_verified` flags remain false. Local byte consistency and candidate/client source commitments do not attest which code a remote process executed. The recorded worker reports the pinned checkpoint revision and BF16 hybrid configuration; broader numerical qualification is documented separately in [numerical evidence](../../verification/evidence/README.md). Synthetic acceptance is not a hidden holdout, broad OCR-quality evaluation or numerical proof.

The retained Waystone allocator snapshot reports 9,180,273,152 allocated bytes, 12,817,793,024 reserved bytes and 11,739,283,968 peak allocated bytes. These are Torch XPU allocator values, not driver-wide dedicated VRAM. A separate Windows observer recorded 4,701,368,320 resident working-set bytes and 20,119,433,216 private committed bytes for the main Python worker; commit is address-space backing, not resident RAM. The second Python process's values are preserved separately in the summary. No driver VRAM measurement or NorthStone process-memory measurement is supplied by these receipts, and the snapshots do not establish complete-process peak memory.

`deployed-lifecycle-01` passed overflow routing, then recorded an incomplete crash phase before the hard reboot interrupted the work. It does not qualify deployed crash recovery or the two real five-minute idle-unload cycles. Resumed lifecycle results must be recorded separately before those claims are made.
