# Correctness before optimization

The current performance target is [sustained throughput on each node](../docs/sustained-throughput.md): completed correct pages per second at the best safe concurrency, guided by a phase-specific roofline model. Short burst latency and routing gains do not establish that ceiling.

The [offline roofline model](roofline.md) estimates vision, prefill and decode arithmetic, ideal shared weight traffic and persistent state as batch size changes. Run `python benchmarks/roofline.py --batch 15` to inspect that hypothetical scenario. It loads no model and leaves empirical hardware ceilings, peak memory and measured pages/sec unknown.

The [preparation receipt](evidence/throughput-preparation-2026-10-04.json) records 31 passing focused CPU tests, source hashes and the remaining live-measurement work. Offline replay tests exercise the scheduler and accounting; they do not qualify GPU throughput.

`throughput.py` provides a rolling-concurrency measurement core and an offline replay CLI. It refills individual vacant slots, preserves a fixed heterogeneous work sequence across concurrency levels, validates every response and retains raw replies. Any failed page invalidates that configuration's rate and stops further configurations. Warmup is recorded separately. The core distinguishes local transport cleanup from independently verified backend drain. This offline CLI never contacts the URL supplied as metadata; its rates are simulator results. The separate [live HTTP adapter](throughput-live-method.md) supports already warm, independently identified nodes under a fresh resource reservation and external monitor. Its [44-test receipt](evidence/throughput-http-preparation-2026-10-04.json) covers fake HTTP and related client checks; hardware drain, a representative corpus and sustained throughput still require live qualification.

For an offline rehearsal, supply the existing `inputs-v2` corpus and a replay JSON mapping each fixture ID to `response_file`, `delay_seconds` and optional `http_status`. Response files are relative to the replay JSON directory and contain complete OpenAI-compatible replies. Use a new output directory. Other fixture schemas are rejected before work starts.

```bash
python benchmarks/throughput.py --replay /path/to/replay.json --direct-url http://127.0.0.1:8000/v1 --corpus benchmarks/inputs-v2 --output /path/to/new-rehearsal --concurrency 1 2 4 --repeat 10
python -m unittest discover -s benchmarks -p test_throughput.py -v
```

The evaluator performs offline comparisons; the explicitly invoked endpoint runner sends only public synthetic fixtures to the endpoint you specify. Neither tool opens Zotero state or dissertation files. `evaluate.py` uses Python's standard library and accepts exported measurements from independently run reference and candidate adapters. No numerical tolerance here is an empirically validated Chandra error budget. The logits gate requires matching reference/candidate identity metadata alongside full-vocabulary arrays and reports target-token log probabilities. Its metadata remains exporter evidence; a self-asserted hash cannot establish independent runtime provenance. Equation gates compare complete Math/Equation/Formula HTML nodes, explicit TeX-delimited nodes or explicit `Equation:` blocks split on semicolons after whitespace normalization. They reject suffixes such as `y = 220` for expected `y = 22`; they do not prove algebraic equivalence. These limitations must be resolved in exporters and stricter semantic adapters before model acceptance.

The retained NorthStone fixture is an installation acceptance test, not an optimization corpus: it contains two known pages, weak equation substring checks, one baseline and one steady repeat, and device-wide memory samples. Its raw response took 22.75 seconds; two-page native/scanned CLI runs took 23.86/24.31 seconds. Those results establish historical compatibility on one shared desktop, not an Intel baseline or a speedup target. The source files inspected are `benchmarks/generate.py`, `benchmarks/ocr.py`, `benchmarks/lifecycle.py`, `stack.json`, `config.json`, `docs/validation.md`, and `evidence/benchmark-baseline.json` in the external `chandra-ocr-uv-rocm` repository.

## Establish an immutable corpus

First import the existing synthetic native/scanned PDFs and expected table through a manifest recording every byte hash, source revision, generator hash and license. Add independently specified fixtures for decimals, signed/exponent quantities, near-confusable glyphs, superscripts/subscripts, multi-column order, tables crossing pages, dense pages near the output allowance, Unicode, blank pages and varied scan quality. Each case needs human-authored semantic expectations and exact accepted equation representations; the reference model's transcription is evidence, never sole ground truth. Render once with pinned renderer/font versions, retain decoded RGB pixels, encoded request image bytes, dimensions, color mode, DPI and both hashes. Prevent encoder differences from masquerading as GPU differences. Hash the transformed tensor including dtype, shape, strides, normalization, resize/interpolation, patch ordering, padding and image-grid metadata. Record exact prompt, template, token IDs, tokenizer/config hashes and special tokens.

Freeze development, calibration and holdout splits before optimization. Holdout images and expectations belong in a separate evaluator-controlled location that the optimizer cannot read; a public manifest contains only identifiers and commitments. A local directory named holdout or an obscure random seed is not hidden. This module creates no hidden holdout and claims no hidden-holdout evaluation. Use exclusive file creation for a new corpus, verify hashes on every run, and issue a new corpus version whenever bytes or expectations change.

## Numerical ladder

A Direct3D device enumeration, buffer transfer and simple shader result test establish hardware smoke only. They cannot establish that Chandra's weights, recurrent state, attention, image encoder or decoding are correct. Keep smoke reports in a separate stage and block model validation claims until model-specific comparisons run.

Use a pinned CPU/PyTorch FP32 reference with fixed inputs, full source/config/model/tokenizer hashes, fixed seeds and explicitly recorded backend/determinism settings. Compare an independent conversion/reload before using candidate precision. Export tensor fixtures for patch embedding, positional transforms, normalization, projections, rotary embeddings, attention/softmax, MLP, image-language bridge and recurrent/GatedDeltaNet state updates. The pinned Qwen3.5 multimodal architecture requires recurrent-state and full-attention coverage; the Whisper encoder/decoder is not a Chandra implementation. Test multiple sequence lengths, image grids, padding masks, state reset, interleaved requests, chunk boundaries and repeated decode steps. Compare both outputs and cache/state after each step, with first-divergence location. Check conversion tensor names, shapes and hashes, not merely parameter counts.

Compare full-vocabulary teacher-forced logits with identical token prefixes at every position, first without caches and then with candidate caches. Retain absolute/relative/RMS error, stable-softmax KL, top-1 agreement, reference top-1/top-2 margin, and target-token log probability. Full-vocabulary argmax agreement is a useful strict initial gate; matching logits at a few positions is insufficient. Small numerical errors near a small margin can change free-running decoding. Teacher-forcing therefore complements full OCR and never replaces it.

For FP32, FP16, BF16 and every quantization configuration, preregister per-operator absolute/relative thresholds, recurrent-state drift envelopes across sequence length, logit/target probability thresholds and semantic OCR gates using calibration data. Quantization provenance includes group sizes, axes, scales, zero points, packing, rounding, accumulation dtype and calibration corpus hash. Start at the highest feasible precision; measure numerical divergence before adding lower precision. Thresholds are unvalidated until measured; generic FP16/BF16 epsilon does not supply a Chandra correctness budget. Require every table cell and numerical quantity, equation, page/order/end marker, metadata invariant and nontruncated finish to pass, with no critical regression against ground truth on hidden holdout. Evaluate whole corpus, not just average character error.

## Export contract and use

`python evaluate.py ocr actual.json --expected expected.json` checks table cells/order, complete normalized equation representations, all end markers, page count/order, metadata geometry/chunks/token accounting and `stop` on every page. Supply `table_rows` from a pinned Markdown parser when the output uses Markdown rather than HTML. `python evaluate.py tensor tensors.json --atol 0.00001 --rtol 0.00001` compares flat same-shape arrays; the exporter must separately enforce dtype, shape and layout identity. `python evaluate.py logits logits.json --atol 0.00001 --rtol 0.00001` compares rows of full-vocabulary logits at identical teacher-forced positions. These command tolerances illustrate syntax and are not accepted budgets. `python evaluate.py manifest corpus.json` verifies file commitments relative to the manifest. `python evaluate.py summary runs.json` refuses failed correctness or profiled runs and reports repeated timings by lifecycle phase.

Expected OCR JSON requires `file_name`, `pages`, `table`, and optional exact `text`, `numbers`, `equations`, `end_markers` lists. Actual OCR JSON requires `text`, `metadata` following Chandra's CLI contract, `finish_reasons` (one per page), and `max_output_tokens`. Existing CLI metadata does not provide finish reasons: adapters must preserve each raw endpoint response rather than fabricate them from the final Markdown. Tensor/logits JSON contains `reference` and `candidate` arrays. Logits JSON additionally requires `reference_context` and `candidate_context` with matching `vocabulary_size`, 40-hex `model_revision`, 64-hex `tokenizer_sha256`, `config_sha256`, `image_sha256`, `prompt_sha256`, explicit `processor_profile` object, `positions`, `prefix_token_ids` and `target_token_ids`. Every row must cover the stated vocabulary, positions must begin at the final prefill index and continue consecutively, and target IDs cover every row or all but the final prediction row. Missing or mismatched identity fails acceptance while available numerical metrics remain visible. Run JSON contains `phase`, `elapsed_seconds`, `pages`, `correctness: {passed: true}`, required `provenance_verified: true`, optional `profiled`, and optional `peak_device_vram_bytes`.

A retained run bundle must additionally identify schema/version, UTC time, corpus split/hash, input and preprocessing hashes, source/compiler/build hashes and flags, Windows/D3D/driver/device/PCI identity, precision/quantization, model/tokenizer/prompt hashes, all request settings, queue/concurrency, raw response/trace paths and hashes, token IDs/counts/finish, correctness report, and resource sampling method/interval. Keep raw JSON/SSE bytes, errors and partial outputs. Device-wide VRAM and process attributable allocations are separate measurements; null means unavailable, never zero.

Only after corpus, numerical and full-OCR gates pass should an optimization enter repeated unprofiled performance comparisons. Repeat separately with process cold and retained compilation cache, compilation cold with a recorded disposable cache, warm idle, and state recreation after idle. Never erase shared caches. Record at least five measurements per phase, page/token distributions, TTFT, total request latency, prefill/decode timings if instrumented, render/write overhead, throughput at fixed concurrency, VRAM peak with sampler interval and CPU memory. Preserve failed runs and report their rate. A profiled run diagnoses cost but does not enter a timing baseline. The summary enforces at least five repeats per lifecycle phase and a true provenance_verified flag; the caller must independently establish that provenance flag, rather than asserting it from OCR pass.

## Endpoint compatibility boundary

The existing service exposes `/v1/chat/completions` with alias `chandra`; raw requests contain a PNG data URL before the exact `ocr_layout` prompt, temperature 0, top_p 0.1 and normal max output 12,384, while the service context is 16,384. Client configuration uses `VLLM_API_BASE` ending in `/v1`, `VLLM_MODEL_NAME=chandra`, and `OCR_ROOT`; CLI invocation is `uv run --no-sync chandra input.pdf output-dir --method vllm --batch-size 2 --no-html`. Retained compatibility references zotero-ocrd commit `84936e6cf78d028dd25f918ea9ee7562695e2dc8`. Benchmark endpoint equivalence with isolated data/review/template roots and synthetic inputs before routing a client to Windows. Preserve raw errors, cancellation, model listing and health behavior; do not reuse the NorthStone lifecycle kill/sleep harness against another implementation without an explicit adapter.

## Integrated public endpoint harness

`generate.py` creates three single-page synthetic development fixtures at 408×528, 816×1056 and 1632×2112 pixels with identical table quantities and distinct end markers. It requires Pillow and an explicitly selected TrueType font; generation records generator/font/Pillow and encoded/decoded hashes, and refuses to replace an existing manifest. There is no hidden holdout in this public corpus. Font rasterization and PNG reproducibility depend on the pinned Pillow/FreeType/font inputs; verify the manifest rather than assume another installation reproduces bytes.

```bash
python benchmarks/generate.py benchmarks/inputs --font /path/to/DejaVuSans.ttf
python benchmarks/endpoint.py --base-url http://HOST:PORT/v1 --corpus benchmarks/inputs-v2 --output /path/to/new-run --provenance /path/to/provenance.json --repeat 5 --phase warm
python benchmarks/endpoint.py --base-url http://HOST:PORT/v1 --corpus benchmarks/inputs-v2 --output /path/to/new-stream-run --provenance /path/to/provenance.json --repeat 5 --stream
python -m unittest discover -s benchmarks -v
```

The runner requires an explicit endpoint, provenance file and new output directory, disables environment proxies, verifies image hashes, preserves request/raw-response/run JSON, and records HTTP errors as failed correctness. Missing content, usage, finish reasons or layout cannot pass. Streaming requires an actual terminal usage event and `[DONE]`; no token estimates substitute for backend counts. Layout checks require normalized finite nonempty bounding boxes, a Table label, exact table cells, specified reading order and terminal marker. Each fixture is one page, so complete fixture iteration is the current page coverage; multi-page CLI metadata acceptance remains the separate `evaluate.py ocr` adapter, and this runner does not establish CLI compatibility by itself.

`--phase process-cold`, `compile-cold` or `recreated` describes only the first request in a run; subsequent requests are warm. The runner neither restarts services nor deletes caches. Independent lifecycle evidence must justify that first phase. Repeated cold measurements require independently prepared runs. TTFT is measured from request initiation to the first received SSE content line; network framing affects that observation. Performance promotion now additionally refuses `provenance_verified` values other than true and fewer than five repeats per phase. The endpoint runner intentionally sets provenance_verified false: exported tensor/prompt-token/runtime provenance must be independently verified before promotion. OCR pass alone never certifies model numerical correctness.

The exact Zotero runner at commit `84936e6cf78d028dd25f918ea9ee7562695e2dc8` was inspected through the GitHub API during integration. It invokes `uv run --no-sync chandra PDF OUTPUT --method vllm --batch-size CONFIGURED_GROUP_SIZE --no-html` from its configured OCR root, supplying `VLLM_API_BASE` and `VLLM_MODEL_NAME`; its private source is not included here. This resolves the earlier direct-source inspection gap.

The checked-in `inputs-v2` manifest is the current development corpus with explicit equation expectations; `inputs` and its byte-matching `generator-v1.py` preserve the original baseline corpus version. No retained NorthStone raw responses or private paths are copied into the public source tree.

## CPU processor reference

`export_processor.py --model /path/to/pinned/model --corpus benchmarks/inputs-v2 --output results/processor-reference` exports exact processor tensor bytes, dtype/shape/strides, image grids, rendered chat prompt and all prompt IDs using local-only Transformers on CPU. Invoke it with an existing interpreter containing the pinned checkpoint-compatible Transformers, Torch and Pillow; it neither loads weights nor installs packages. The exporter checks committed model processor/config/tokenizer files and encoded/decoded fixture hashes before processing. Keep exports under ignored `results/`; the report records runtime versions and leaves `provenance_verified` false because processor evidence alone cannot validate the inference runtime or model numerics.

The processor exporter accepts `--profile checkpoint-default` (the default checkpoint size settings) or `--profile northstone-serving` (explicit `size: {shortest_edge: 3136, longest_edge: 3145728}`, matching the existing serving worker). The report records the selected profile and exact overrides. On the frozen corpus the CPU export observed prompt token counts 801/1451/3959 with checkpoint defaults and 801/1451/3617 with the serving profile; representative image grids were `[1,132,102]` and `[1,126,96]` respectively. A candidate must select the same explicit profile as its reference.

## Two-page CLI acceptance

`cli-inputs-v1` freezes two entirely synthetic PDFs with identical prose, two-column reading order, six simple equations, two exact tables and separate page-end markers. `native.pdf` has an embedded text layer; `scanned.pdf` contains only page images rasterized at 144 DPI with a 0.25-pixel Gaussian blur. The manifest commits both PDFs, all four 192-DPI RGB page renders, decoded pixels, font/generator hashes and ReportLab/Pillow/PDFium versions. Regeneration with the recorded versions/font produced identical file commitments; all four page renders were visually inspected. The synthetic text is CC0; the embedded DejaVu font retains its notice in `DejaVu-LICENSE.txt`. This public development fixture is a compatibility test, not a generalization corpus.

```bash
uv run --no-sync python benchmarks/generate_cli.py /path/to/new-corpus --font /path/to/DejaVuSans.ttf
uv run --no-sync python benchmarks/cli_acceptance.py --base-url http://HOST:PORT/v1 --corpus benchmarks/cli-inputs-v1 --output results/new-cli-run
```

The runner verifies frozen file commitments and invokes `uv run --no-sync chandra PDF OUTPUT --method vllm --batch-size 2 --no-html` separately for each fixture. It supplies explicit `VLLM_API_BASE`/`VLLM_MODEL_NAME`, isolates HOME/XDG/HuggingFace/uv state and preserves stdout, stderr, output hashes, command, metadata and elapsed time in a new output directory. The checks require two pages in order, all specified content/table cells/equations/end markers, positive per-page token/chunk counts, consistent totals, finite nonempty geometry and no saved HTML. CLI exceptions can be swallowed by the upstream CLI, so missing files or content fail regardless of its exit code. This runner performs no service restart or cancellation; a CLI timeout leaves endpoint work potentially active, and OpenAI SDK transport retries may still occur (its constructor default remains two). The runner sets and records `MAX_VLLM_RETRIES=0` to disable Chandra generation retries that alter temperature; this does not disable SDK transport retries.

CLI metadata does not retain endpoint stop reasons. Reports therefore record `finish_reasons: null`, `truncation_verified: false`, `full_ocr_acceptance: false` and `provenance_verified: false` even when CLI content/metadata checks pass. Keep this result alongside the separate raw endpoint corpus that checks stop reasons; never fabricate stops from Markdown or promote CLI timing into a numerically accepted baseline.

`recorded_cli.py` closes that observation gap without changing Chandra internals. It runs a temporary loopback proxy that forwards each request once, preserving actual HTTP request/response bytes, hashes, status, stop reasons and usage. Decoded request pixels must uniquely match a frozen rendered page after the installed client's `scale_to_fit`; arrival order is never used to infer page identity. The combined gate requires complete CLI content/metadata, one observed successful completion per page, genuine `stop` reasons and exact per-page token-count agreement. Retries, duplicate pages, ambiguous pixels and missing metadata fail this gate. This remains synthetic document acceptance, with independent runtime/numerical provenance required separately.

```bash
uv run --no-sync python benchmarks/recorded_cli.py --upstream-base-url http://HOST:PORT/backends/waystone/v1 --corpus benchmarks/cli-inputs-v1 --output results/new-recorded-cli --timeout 900
```

Sparse teacher-forced exports may additionally provide matching `teacher_token_ids` containing the complete forced response sequence. In that mode positions must be increasing and unique within the base-prefix/teacher sequence, and each target ID must equal the forced token at its selected position. This permits selected full-vocabulary rows spread across a long response without implying unsampled positions were checked.

## Bounded live integration

`live_integration.py` coordinates the exact two-PDF CLI acceptance, all three PNG endpoint fixtures, a separate warmup followed by at least five warm repetitions, two overlapping requests, and stream cancellation followed by bounded drain and complete recovery OCR. It never starts/restarts services, changes model settings or retries an endpoint-harness POST. The exact CLI disables Chandra generation retries through `MAX_VLLM_RETRIES=0`; OpenAI SDK transport retries remain a separate client behavior. Specify a service window with the GPU coordinator before invoking it. An explicit `--stages` subset permits incremental acceptance without repeating already retained work.

```bash
uv run --no-sync python benchmarks/live_integration.py --base-url http://ROUTER:PORT/v1 --cli-base-url http://ROUTER:PORT/backends/waystone/v1 --backend waystone --provenance /path/to/runtime-provenance.json --output results/new-live-integration --request-seconds 900 --drain-seconds 120 --budget-seconds 3600
```

The PNG requests carry `X-Chandra-Backend`; the exact CLI uses the separate selector base URL because it cannot send that custom header. Before submitting inference the runner requires observable zero ownership through `/health` and the `chandra` model alias. It checks actual generated content, layout, table cells, equations, markers, backend usage and stop reasons. Warm timings use `tiny` by default to bound cost; `--warm-fixture representative` selects the larger fixture explicitly. Median/min/max times and token counts describe only the selected fixture, and numerical/provenance promotion remains false. No teacher-forced logits substitute for free generation.

Concurrency streams the tiny fixture while submitting the distinct small fixture; successful complete OCR or a single HTTP 503 capacity rejection is valid for the contender. Service ownership must be observed during the primary request, and every accepted output must match its own fixture. Cancellation closes a stream after actual content and before receiving `[DONE]`, preserves partial raw SSE bytes, observes bounded drain through health, then checks a fresh complete tiny OCR response. A buffer already containing terminal completion cannot prove cancellation. These black-box observations establish drain/recovery behavior; backend traces remain necessary to establish exact stop timing and replay counts. On a global deadline the runner closes its HTTP streams and terminates its task-owned CLI process group; already submitted remote generation may remain active, so inspect health before further allocation.

`deployed_lifecycle.py` tests the installed project services during an exclusive synthetic workload window. Its `overflow` phase occupies both NorthStone slots before checking automatic selection of Waystone. Its `crash` phase waits for actual streamed content, verifies the installed worker unit's ownership receipt, kills only that unit's main process, and checks incomplete output, one automatic restart, quarantine recovery and subsequent correct OCR. Its `idle` phase performs two real five-minute idle intervals with passive health/model polling, requiring zero PyTorch allocated/reserved bytes and correct OCR after reload. The default run includes all three phases and ends with the Windows model unloaded; `--phases` selects a subset. It never retries an inference POST or mutates unrelated services.

```bash
uv run --no-sync python benchmarks/deployed_lifecycle.py --base-url http://127.0.0.1:8002/v1 --worker-base-url http://127.0.0.1:18001/v1 --provenance /path/to/runtime-provenance.json --output results/new-deployed-lifecycle --phases overflow crash idle --budget-seconds 1800
```
