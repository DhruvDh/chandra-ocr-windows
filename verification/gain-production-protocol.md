## A precise prospective memory gate

The retained inventory contains 65 gains of 10,240 bytes and 16 of 1,024 bytes: 681,984 logical bytes. The pinned native XPU allocator rounds requests to 512 bytes, splits small blocks when at least 512 bytes remain, and charges allocated block size. Every gain already fits that granularity, so this path warrants no additional allocation-rounding allowance. Its 2 MiB small-pool segment size concerns reserved memory. These are conditional source conclusions, not a measurement of the loaded process. See the pinned [allocation implementation](https://github.com/pytorch/pytorch/blob/5c4886908584029761b579af026dcfb627c84070/c10/xpu/XPUCachingAllocator.cpp) and [allocator constants](https://github.com/pytorch/pytorch/blob/5c4886908584029761b579af026dcfb627c84070/c10/core/AllocatorConfig.h).

Record relevant allocator settings before importing Torch. Require the pinned native allocator with no custom allocator, private pool, graph capture or compilation. Establish resource admission separately from Torch allocation counters, retaining unchanged execution concurrency and one owned model process. On the current Windows account, global counters are unavailable; the separately reviewed admission method uses supported [DXGI process-local budgets](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/nf-dxgi1_4-idxgiadapter3-queryvideomemoryinfo), physical device binding, a stock-allocation calibration, continuous same-process queries and an independent system-RAM guard. The completed numerical trial required 14 GiB headroom before Torch and after context initialization, capped additional DXGI usage at 12 GiB, and retained 2 GiB unused budget. These are process-local observations, not global free VRAM or a reservation. Forecast each later workload against its separately frozen limits; retain the original comparison method and all earlier admission records.

Synchronize before each memory boundary. Gain installation must increase current allocated bytes by exactly 681,984. Reset request peak counters after installation, then require each candidate request peak to be no greater than its paired original peak plus 681,984 bytes. At matching completed-request boundaries, live gains must account for exactly that current-allocation difference. Compare immediately before and after closing the gain scope to require release of precisely its gains; closing gains does not remove state created by inference. The first excluded original warmup must pass correctness before establishing the fixed steady allocation reference, with its initialization delta recorded separately. Every later pre-install and post-close allocation must match that reference. Report setup, request and teardown peaks separately, and report reserved-memory values without using reservation granularity to excuse excess allocated bytes. Any unexpected reservation growth needs review before continuing; it is not an automatic exemption.

After final unload and synchronization, require zero Torch allocated and reserved bytes and verify the owned process has ended. A missing measurement, unexpected allocation, timeout or ownership failure stops the sequence without promotion. Keep the earlier 1,241,088-byte peak increase and unresolved policy decision intact; this stricter prospective gate does not retroactively qualify that run.
