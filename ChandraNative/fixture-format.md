# External trained recurrence fixture v1

The JSON schema identifier is `chandra.native.delta.v1`. The metadata and binary payload remain private run artifacts. A retained result binds the metadata SHA-256, complete payload SHA-256, per-tensor SHA-256, pinned model revision and CPU source hash; the summary may publish those hashes and aggregate errors without copying activations or source input text. The parser uses vendored [nlohmann/json 3.12.0](https://github.com/nlohmann/json/releases/tag/v3.12.0), with its MIT license and release-published header hash preserved in `vendor/nlohmann/`. Windows hashing uses BCrypt SHA-256; the optional portable CPU checker uses the installed OpenSSL library on Linux.

The root contains exactly `schema`, `dtype`, `byte_order`, `payload_file`, `payload_bytes`, `payload_sha256`, `model_revision`, `source`, `semantics` and `tensors`, plus an optional `context` provenance object. `dtype` is `float32`, `byte_order` is `little`, and the model revision is `af93b47dba1b47b6640c86ccf487ed2260ab9a09`. `payload_file` is a local ASCII basename; no directory separators or traversal components are accepted. JSON metadata is bounded to 1 MiB and payload to 512 MiB. Duplicate JSON keys, unknown root fields and non-integer dimensions or offsets are rejected. The `source` object carries the export layer/function and model source hash; optional `context` carries input/processor/tokenizer hashes and related provenance. Neither object is executed.

`semantics` has exactly seven fields: `q=l2_normalized_scaled_sqrt_keydim`, `k=l2_normalized`, `g=negative_log_decay`, `beta=post_sigmoid`, `heads=expanded_value_heads`, `initial_state=zeros`, and `layout=THD`. Exporters apply the installed graph's FP32 `x * rsqrt(sum(x*x)+1e-6)` normalization, expand key/query heads to value heads when required, and scale Q by `key_dimension**-0.5`; the native kernel applies none of those transformations again. G and beta must already include the learned model transformations. Prefill starts with a zero recurrent state. A fixture with another initial state or tensor stage needs a new schema or an explicit implementation change.

`tensors` contains exactly `q`, `k`, `v`, `g`, `beta`, `expected_output` and `expected_state`. Every descriptor has exactly `shape`, `offset_bytes`, `byte_length` and `sha256`. Binary serialization order is Q, K, V, G, beta, expected output, expected state; byte ranges must be contiguous and cover the entire file without holes, overlaps or trailing bytes. Q/K shapes are `[T,H,K]`; V and expected output are `[T,H,V]`; G/beta are `[T,H]`; final state is `[H,K,V]`. All values are finite, G is nonpositive and beta lies in [0,1]. The importer also checks the upper normalization envelope `sum(q*q) <= 1/K + 1e-4` and `sum(k*k) <= 1.0001`; these bounds catch common stage mistakes but do not prove a provenance declaration. Current kernel bounds are T≤4096, H≤32 and K/V≤128. The graph's expected output is before gated RMSNorm and output projection.

`chandra-native.exe --fixture fixture.json --fixture-sha256 expected-metadata-hash --pci bus:device.function --shader-dir shader-directory` runs the GPU check. The expected metadata hash is optional at the CLI boundary but should be supplied when replaying a retained fixture. `--validate-fixture` checks the complete format and hashes before any GPU device creation. `fixture-check.exe fixture.json` checks the CPU FP32 and double recurrence against expected outputs/state without creating a GPU device. The GPU run checks the trained source reference, CPU FP32 and double oracles, prefill/decode equivalence, and state/output reset. The reference/CPU gates use the unchanged absolute tolerance 2e-5 with no relative allowance; decode/prefill and reset must agree exactly. These are fixture-specific correctness gates, not a model-wide accuracy claim.

`test_fixture_format.py path-to-native-fixture-checker` exercises the actual native importer using a hand-calculated scalar case and malformed fixtures: payload/tensor hash mismatches, overlap, zero/fractional/overflow dimensions, wrong normalization stage, revision mismatch, path escape, unknown fields, truncation, duplicate keys, nonfinite values, positive decay, beta outside its range and normalization-envelope violations. It runs entirely on CPU, stores temporary fixtures only for the test duration and reports each unexpected acceptance or rejection.

Adapter selection is independently bound through DXGI vendor/device/subsystem/revision, LUID and a WDDM PCI address obtained with [D3DKMTOpenAdapterFromLuid](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmthk/nf-d3dkmthk-d3dkmtopenadapterfromluid) and [D3DKMTQueryAdapterInfo](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmthk/nf-d3dkmthk-d3dkmtqueryadapterinfo). `--list-adapters` enumerates this identity without creating a D3D device. Sentinel addresses outside valid bus/device/function ranges remain explicitly unavailable and are refused for selection. `--pci` selects the physical board; `--luid` supplies a session-specific logical guard. If multiple candidates still match, selection fails until the caller provides another explicit guard. A DXGI ordinal is an optional additional restriction, not durable board identity, and LUID can change after driver/boot transitions.
